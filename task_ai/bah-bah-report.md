# Бах-бах-Репорт — входящие баги и фичи

Сырой inbox наблюдений из живого тестирования LearnOS. Пишет скилл
`.zcode/skills/bah-bah-report` (ZCode) по фразам «запиши баг-репорт» / «запиши идею фичи»:
он интерпретирует слова пользователя, коротко разбирается в коде (read-only) и кладёт
запись сюда. В момент записи ничего не исполняется и не исправляется.

Когда накопится — «запусти бах-бах на исправление»: open-записи группируются по областям
кода (без пересечений по файлам) и последовательно уходят агенту learnos-dev.

Статусы: `open` (записано) → `tasked` (взято в работу) → `fixed` (ссылка на задачу/коммит).
Связь с реестрами: известные баги — `bugs/BUG-…`, задачи — `../tasks/`; ссылки на них живут
в поле «Связано», записи дублируются в реестры только при фазе исправления.

## Баги

### BB-002 · bug · fixed · 2026-11-10 · Веб-поиск медленный: цепочка и академ-агрегат последовательны

- **Симптом:** поиск агента (web_search в research-режиме) ощутимо медленный — до первых результатов проходят десятки секунд.
- **Ожидание:** первый осмысленный ответ за единицы секунд; падение одного звена не должно удлинять ожидание.
- **Как устроено:** web_search идёт через `ChainProvider` — провайдеры опрашиваются строго по очереди до первого непустого (serper/tavily → ddg → wikipedia → hackernews), таймауты 10–20 с на звено (`server/app/modules/research/providers.py:332`); при полной пустоте все звенья опрашиваются ВТОРОЙ раз (`providers.py:346`). Академ-агрегат тоже последовательный: arXiv + OpenAlex + Semantic Scholar по 15 с, S2 ещё спит 2 с на 429 (`server/app/modules/research/service.py:184`). Кеш 20 мин и single-flight есть (`service.py:245`) — повторные запросы быстрые, первый медленный.
- **Гипотеза:** без ключей Tavily/Serper голова цепочки — DDG (анти-бот, таймаут 15 с), дальше wiki/HN; худший сценарий ≈ 45–60 с. Лечится параллельным fan-out («первый непустый забирает ход») и урезанными таймаутами.
- **Воспроизведение:** research-сообщение в чате на продах без ключей поиска.
- **Контекст:** веб/прод CT 132.
- **Связано:** BB-003 (второй источник медленности — сама модель), T-014 (research v2, Э3–Э5 открыты)
- **Исправлено:** [T-055](archive/2026-11-10-T-055-parallel-search.md) (коммит `7419ce5`; ChainProvider — параллельный fan-out «первый непустой побеждает» без второго прохода, академ-агрегат — параллельно, таймауты ddg 8/wiki 6/hn 6/tavily/serper 10 с; тесты 436, прод: web_search 1.1–1.3 с вместо десятков секунд)

### BB-006 · bug · open · 2026-11-10 · YouTube-обработка: 429-буря и отсутствие ignore-errors роняют субтитры

- **Симптом:** обработка YouTube-видео часами висела в processing и падала; после восстановления прокси скачивание субтитров падает на первом языке с HTTP 429 — второй язык даже не пробуется, а ошибка в job («субтитры не найдены (ru/en)») не показывает причину.
- **Ожидание:** падение одного языка не роняет остальные (en докачивается, если ru в 429); ограниченные ретраи без бесконечной бури; stderr yt-dlp попадает в error job'а.
- **Как устроено:** `server/skills/youtube-to-summary/run.py:70-96` — yt-dlp зовётся без `--ignore-errors` (упал ru 429 → exit 1, en не пробуется) и без `--retries`/`--sleep-requests` (первая обработка с 11:14 ушла в часовую retry-петлю и заработала 429-бан timedtext на IP); комментарий про «ненулевой код при 429 у одного языка» уже есть, но флага нет. Кеш-папка data/youtube пуста — повторной обработки без сети не получается. Whisper-фолбэк не реализован.
- **Гипотеза:** `--ignore-errors` + `--retries 2` (+ аккуратный `--sleep-requests`), прокидывание stderr в ошибку; опционально кеш готовых .vtt как готовый результат без сети.
- **Воспроизведение:** прод CT 132, src_40fdcabd / src_4425608e, jobs 18–21 (2026-11-10).
- **Контекст:** веб/прод CT 132; инцидент 2026-11-10: прокси xray потерялся из app_settings (см. доп. контекст в истории), восстановлен вручную как socks5://xray:1080.
- **Связано:** T-014 (research v2), T-017 (скилл-система)

### BB-003 · feature · fixed · 2026-11-10 · Модели по ролям: быстрые операции — на лёгкую модель

- **Идея:** у провайдера z.ai есть быстрые и думающие модели GLM; навешивать на агентов подходящие: категоризация блоков, summary глав, интенты, простые tool-задачи — быстрая модель; разбор главы, фейнман, планирование курса — думающая.
- **Зачем:** сейчас все четыре роли llm.yaml (chat/structured/fast/vision) указывают на одну тяжёлую glm-5.3 (`server/config/llm.yaml:12`) — «быстрые» агенты сидят на думающей модели, это заметная часть медленного отклика и расхода квоты.
- **Куда приляжет:** механизм уже есть — у каждого агента своё `model_role` (`server/app/modules/chat/agents.py:149`, `knowledge/agents.py:70-86`, `library/agents.py:46-67`, роутер `server/app/llm/router.py:80`); нужно (а) раздвинуть роли по моделям в llm.yaml, (б) по ТЗ — конфиг ролей из UI с горячей перезагрузкой (этап 10-B), (в) опционально свои роли у отдельных субагентов/скиллов, а не только 4 глобальные.
- **Дополнение 2026-11-10:** уточнение пользователя — думающая модель только на обучение: диалог по найденному материалу, фейнман, создание учебного материала (роль `chat` + разборы); всё тривиальное (категоризация, summary, интенты, tool-обвязка) — самые быстрые модели с выключенным «раздумьем». Сейчас thinking/reasoning не управляется вовсе — в wire-запрос уходят только temperature/max_tokens (`server/app/llm/providers/openai_compat.py:147-195`), нужен per-role params (thinking/reasoning_effort) как capability провайдера. Второе требование — не привязываться к z.ai: уход на другого OpenAI-совместимого провайдера правкой конфига ролей, не кода (z.ai-специфика уже изолирована в адаптере: content=null при tool_calls, json_schema через системное сообщение; пресеты провайдеров прописаны в ТЗ 10-B).
- **Связано:** ТЗ этап 10-B ([stages/10-settings-and-cloud.md](stages/10-settings-and-cloud.md)), BB-002, BB-004
- **Исправлено:** [T-056](archive/2026-11-10-T-056-llm-roles-and-status.md) (коммиты `33e6b6c`, `dba474b`) — fast/structured → `glm-5.3-flash` + `params.thinking: disabled` (смоук: reasoning_content исчезает, completion_tokens 157→5), chat остаётся думающей `glm-5.3`; per-role params прокинуты RoleBinding → `resolve()` → `extra_body` (шорткат thinking нормализуется в адаптере, bad_request на параметр — дроп + один ретрай, без зацикливания); пресеты OpenRouter/OpenAI/DeepSeek закомментированы в llm.yaml. Полный этап 10-B — постановка [T-057](tasks/T-057-llm-roles-ui.md)

### BB-004 · feature · fixed · 2026-11-10 · Цепочка GLM-ключей — панель в настройках

- **Идея:** в настройках видеть состояние цепочки ключей (ZAI_API_KEY..4): какие подключены, какой рабочий сейчас, какие в cooldown и когда сброс; управлять порядком.
- **Зачем:** ротация есть и работает (`server/app/llm/providers/openai_compat.py:80-113` — sticky-индекс, cooldown ~10 мин), но снаружи виден только счётчик `keys: N` в `/api/health` (`server/app/llm/router.py:127`) — какие ключи юзаются и в каком состоянии, узнать нельзя.
- **Куда приляжет:** метод статуса у OpenAICompatProvider (cooldown-карта + sticky) → router.status() → блок в health/API; экран веб-настроек «Прокси и поиск» (`web/src/app/settings`, `/api/connectivity`) — рядом или отдельным блоком «LLM»; по ТЗ — этап 10-A (SecretStore) и 10-B.
- **Связано:** T-040 (цепочка ключей), ТЗ этап 10, BB-005
- **Исправлено:** [T-056](archive/2026-11-10-T-056-llm-roles-and-status.md) (коммит `dba474b`) — `OpenAICompatProvider.keychain_status()` (номера, sticky, cooldown-остатки; значения не отдаются) → `ModelRouter.detailed_status()` → `GET /api/llm/status` под bearer-токеном (health без детализации); блок «LLM» в настройках рядом с «Прокси и поиск»: карточки ролей (модель/провайдер/params) и цепочка ключей с индикаторами и обратным отсчётом cooldown (обновление кнопкой и раз в 30 с)

### BB-005 · feature · fixed · 2026-11-10 · Root-агент видит состояние LLM и может переключить ключ

- **Идея:** root-агент знает состояние своей системы: какой моделью/ключом работает, какие ключи в cooldown — и сам может сбросить cooldown или переключить ключ.
- **Зачем:** при «все ключи в cooldown» (LLMError rate_limit) агент сейчас беспомощен; тул `search_providers` уже показывает состояние поиска (`server/app/modules/research/tools.py:106`), аналога для LLM-слоя нет.
- **Куда приляжет:** новый тул `llm_status` (опционально `llm_key_reset`) рядом с search_providers — реестр инструментов + модуль LLM; источник данных тот же, что для BB-004 (router.status() + cooldown-карта провайдера).
- **Связано:** BB-004 (данные те же, поверхность другая), T-034 (оркестратор)

### BB-007 · feature · open · 2026-11-10 · Агент сам создаёт субагентов: тул draft+create для root

- **Идея:** в разговоре с root-агентом сказать «сделай себе агента под X» — агент сам генерирует черновик (имя/описание/промпт/инструменты) и создаёт его, без захода в UI.
- **Зачем:** весь механизм уже есть, но доступен только человеку через UI: LLM-конструктор `draft_custom_agent` (`server/app/modules/tuning/service.py:417`, агент agent_designer с каталогом тулов) и `create_custom_agent` (`:443` — БД + живая регистрация в реестре без рестарта, `agent/registry.py` upsert_custom). Субагенты из чата запускаются (`run_agent`/`list_agents`, глубина ≤2), а создавать новых агентов агент не может.
- **Куда приляжет:** два новых тула рядом с run_agent — `draft_agent` (бриф → черновик) и `create_agent` (создание через offer_action-подтверждение, как research-источники в T-048); guard-лист: новому агенту нельзя выдавать чувствительные тула (revision, tuning) и лимит числа кастомных.
- **Связано:** T-034 (закрыт — субагенты), T-017 (скилл-система), T-048 (offer_action-паттерн)
- **Исправлено:** [T-056](archive/2026-11-10-T-056-llm-roles-and-status.md) (коммит `33e6b6c`) — тул `llm_status` (module="llm", виден root-агенту в веб/MCP): роли → модель/провайдер/params, по провайдеру — цепочка ключей (номера, sticky, cooldown; значений нет); `reset_cooldown: true` очищает карту cooldown провайдеров — агент сам «переключает ключ» после исчерпания квоты и продолжает
