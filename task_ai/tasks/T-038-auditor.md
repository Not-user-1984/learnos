## Что нужно

Саморевизия без самоуничтожения, по ступеням из T-034 (решение пользователя:
строим ступени 1–2; ступень 3 — авто-пуш в main — отдельным решением позже,
предусловие — авто-rollback в deploy-скрипте CT 132 в репо proxmox). Работаем
в ветке `t-034-orchestrator`.

1. **Субагент `auditor`** (builtin, модуль chat или отдельный):
   - инструменты **read-only по коду репо**: `repo_list(path)` — листинг дерева
     (без `data/`, `kb/`, `.git`), `repo_read(path)` — чтение файла с лимитом
     размера; корень репо определяется настройкой (на проде — рабочая копия
     deploy'я; на маке — сам репо);
   - задача аудита формулируется пользователем или root-агентом («посмотри,
     почему X тормозит», «предложи, что упростить»); выход — находки с
     файлами/строками;
   - инструмент `create_task_file(title, body)` — запись задачи в
     `task_ai/tasks/` (формат по шаблону из `task_ai/tasks/README.md`, только
     создание, статус idea; не перезаписывает существующие).
2. **Ступень 2 — git-инструмент агента** (после того как auditor приживётся,
   отдельным коммитом в этой же задаче):
   - `git_prepare_change(branch, files, commit_message)`: записать правки
     (переданные файлами) в новую ветку в рабочей копии, коммит; **никогда** не
     трогает main, не пушит в main;
   - guard-лист (проверка до записи): `server/app/bootstrap.py`,
     `server/app/main.py`, `server/alembic/**`, `server/app/llm/**`,
     `server/config/llm.yaml`, `docker-compose*`, deploy-скрипты, сам модуль
     guard'а, `web/` (первоначально — только сервер; веб агенту не нужен);
     попытка правки из списка — отказ с предложением создать задачу;
   - карточка `git_change` в чат: ветка, дифф-стат, сообщение коммита, кнопки
     «Посмотреть»/«Отклонить»; применение/пуш — только человеком или внешним
     контуром;
   - budget: не более N подготовленных веток в день (настройка, по умолчанию 3).
3. **Запуск тестов агентом** (для качества коммита): инструмент `run_checks(scope)`
   — ruff+pytest (по wedge: только server); агент готовит коммит только с
   зелёными проверками.

### Решения (выбраны простейшие)

- **Worktree вместо checkout**: ветки живут в `data/git-worktrees/<branch>` —
  рабочая копия никогда не покидает main; deploy-таймер (fetch+reset main) их
  не затрагивает, как и untracked-файлы задач из create_task_file.
- **Ветки только `agent/<имя>`** (валидируется): reject-эндпоинт физически не
  может удалить чужую ветку; бюджет считается по дневнику
  `data/git-branches/<дата>__<ветка>.json` (переживает удаление веток).
- **Коммит — только с зелёными проверками, гваром в коде**: git_prepare_change
  сам гоняет SERVER_CHECKS (ruff/format/lint-imports/pytest через `uv run`,
  cwd = worktree/server) до коммита; красные → worktree и ветка удаляются,
  ошибка checks_failed с хвостами логов. Агент не может закоммитить красное
  в принципе. Отдельный инструмент run_checks — для свободной проверки (в
  рабочей копии или worktree ветки).
- **Guard-лист** ровно по T-034 + task_ai/ + deploy/ + весь модуль revision
  (само-охрана); docker-compose* — по первому сегменту пути.
- **Ступени 1–2 одним серверным коммитом**: оба набора инструментов живут в
  одном сервисе и идут одним ревью ветки; отдельный коммит — веб-карточка.
- **Кириллица в title задачи** не транслитерируется: slug пустой → файл
  `T-0NN.md` (номер уникален); латиница → `T-0NN-slug.md`.
- Тесты обёртки run_checks — на подменных командах (monkeypatch SERVER_CHECKS):
  тестируется поведение (коды выхода, хвост лога), не линтеры.

### Прод-выкат (после мерджа, отдельный шаг)

- Смонтировать рабочую копию репо в контейнер rw (worktree пишет в её .git):
  например `../:/repo` + `LEARNOS_REPO_ROOT=/repo` в `/opt/learnos/.env`;
  read-only недостаточно для ступени 2.
- `run_checks` требует `uv` в контейнере: если нет — вернёт код 127 с понятным
  логом; при необходимости доставить uv в образ server отдельной задачей.
