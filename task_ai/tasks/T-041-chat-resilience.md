## Что случилось (следствие по agent_runs, прод)

Пользователь попросил добавить видео (12:33:50). Root-агент ушёл в длинную
автономную цепочку: сам работал ~4.5 мин, позвал субагента free_chat (19 шагов,
18 инструментов, 210 с — ок), запустил второй субагент (12:45:10) — и в этот
момент контейнер сервера был пересоздан деплоем (выкат ключей). Результат:
запуски навсегда зависли в `status='running'`, **ответ так и не сохранился**,
пользователь вернулся — пусто. Уход со страницы при этом НЕ убивал генерацию
(фоновая задача жила) — убивали её рестарты контейнера и, возможно, обрывы
долгого SSE.

Три корневые проблемы:
1. У клиента нет правды о состоянии: открыл разговор — не видно, что агент
   ещё работает (или что генерация прервана).
2. Рестарт сервера (а деплой = рестарт каждые пару пушей) убивает генерацию
   молча: зависшие `running`-строки, ни ответа, ни извинения.
3. Авто-догон ответа на клиенте ограничен 180 с — длинные автономные цепочки
   (10+ мин) выпадают.

## Что нужно

1. **Сервер, старт**: `agent_runs` со `status='running'`, созданные до старта
   процесса, помечать `status='interrupted'`, error='процесс перезапущен'
   (id запусков, живых на момент старта, знать нельзя — помечаем все старые
   running; место: bootstrap/startup hook после миграций).
2. **Сервер, API правды о состоянии**: в `GET /api/conversations/{uid}` (detail)
   добавлять блок `agent_state`:
   - `working: bool`, `runs`: живые запуски этого разговора (root + субагенты по
     parent-цепочке от root-запуска разговора): agent, steps, tool_calls,
     started_at — источник `agent_runs` (status='running' и свежие < 2 ч);
   - `interrupted: bool` — последний user-message без assistant-ответа И есть
     недавние (сегодня) `interrupted`-запуски этого разговора.
3. **Сервер, resume**: `POST /api/conversations/{uid}/resume` — если последнее
   user-сообщение без ответа: запускает генерацию заново по нему (без дубля
   user-сообщения, стандартный stream_reply-цикл с SSE как у messages).
   Если уже есть живые running-запуски — 409 «агент уже работает».
4. **Веб, живой статус**: при открытии разговора и при отсутствии ответа на
   последнее user-сообщение:
   - `working` → бейдж «агент работает: root · шаг 3 / субагент free_chat»,
     поллинг detail каждые 5 с, при появлении ответа — подгрузить его
     (лимита 180 с НЕТ; поллинг живёт, пока вкладка открыта; on mount тоже);
   - `interrupted` → баннер «генерация прервана (перезапуск сервера)» +
     кнопка «Продолжить» → resume → снова working-режим;
   - обычный авто-догон после обрыва стрима сохраняется, ноCap 180 с убрать
     в пользу общего поллинга по agent_state.
5. **Тест на разрыв читателя**: api-тест — клиент читает SSE и обрывается
   посреди стрима → ответ всё равно сохраняется в БД (FakeLLM с задержкой).

## Критерии готовности

- [ ] api-тест: обрыв SSE-читателя не теряет ответ.
- [ ] api-тест: startup помечает старые running → interrupted; detail отдаёт
      agent_state (working/runs/interrupted).
- [ ] api-тест: resume дорабатывает последний user-message; при живых
      running — 409.
- [ ] Веб: бейдж работы с шагами, баннер прерывания с «Продолжить», поллинг
      без 180с-лимита; lint+tsc+build зелёные.
- [ ] Сервер: ruff/format/lint-imports/pytest зелёные.
- [ ] Коммиты в ветке `t-041-chat-resilience`; «ждёт ревью ZCode» в файле задачи.

## Заметки

- Деплои частые (git push = рестарт): молчаливые потери недопустимы —
  interrupted+resume это закрывает; полную докатку прерванной генерации
  (продолжить с середины) не делаем, resume = перезапуск ответа.
- Прогресс по шагам в agent_state берём из агрегатов agent_runs (steps уже
  пишутся на finish; для живого steps можно брать max(id) обновлением на
  каждом tool_start — если дёшево: обновляйте steps инкрементально в runtime,
  иначе показываем только «работает: agent»).
