## Что нужно

Когда агент в диалоге что-то спрашивает или предлагает варианты («дальше /
подробнее / сессия по главе?», «сохранить конспект?», «перейти к следующей
главе?»), пользователь печатает ответ руками. Нужно: к таким вопросам агент
прикладывает сгенерированные кнопки — короткие варианты ответа; клик = отправка
сообщения. Писать «дальше» текстом больше не нужно.

Контекст: механизм карточек уже есть — action_offer (T-036) с кнопками Да/Нет
и блокировкой после клика (T-044). Для вариантов «дальше/подробнее/сессия»
нужна карточка с произвольным набором коротких ответов (quick replies),
не только Да/Нет.

## Что сделать

- Карточка `quick_replies` (или расширение action_offer): список коротких
  вариантов (2–4), клик отправляет текст варианта как обычное сообщение,
  кнопки блокируются после клика (как в T-044: «отправлено — агент работает…»).
- Канал доставки: SSE-карточки к сообщению агента (уже существующий механизм
  live-cards) — агент прикладывает варианты структурированно, UI не угадывает
  вопросы парсингом текста.
- Промпты агентов (quick_reviewer, session_tutor, root): в местах, где агент
  предлагает выбор (п.3 quick_reviewer «дальше / подробнее / сессия», конец
  главы, предложение конспекта) — прикладывать карточку вариантов.
- Дизайн — по DESIGN.md, токены, обе темы; компактно, над инпутом или в теле
  сообщения — на усмотрение разработчика + визуальная полировка ZCode.

## Критерии готовности

- [x] В быстром разборе после главы агент предлагает «дальше / подробнее /
      сессию» кнопками — клик отправляет ответ, печатать не нужно.
- [x] Предложение конспекта/сохранения тоже с кнопками.
- [x] Кнопки блокируются после клика (нет дублей, T-044-поведение).
- [x] Карточки не ломают обычные ответы без вариантов; старые разговоры
      отображаются без ошибок.
- [x] Тесты: сервер — карточка доходит в SSE; веб — рендер и клик.

## Заметки

- Это закрывает ежедневную боль из быстрого разбора Кафки — приоритет высокий.
- Решение: отдельный инструмент `offer_replies` вместо расширения
  `offer_action` — семантика разная (короткий выбор ответа vs согласие на
  действие с Да/Нет), контракт заказчика «новый тип карточки quick_replies».
- Карточка приходит событием `card` в момент вызова инструмента (паттерн
  существующих карточек); кнопки кликабельны только после конца стрима
  (`onSend = streaming ? undefined : send` в chat-view) — т.е. фактически с
  финальным сообщением, как требовал контракт.
- Поведение клика повторяет action_offer (T-044): локальная блокировка
  «отправлено…» + серверный 409-гвард `ensure_idle` до сохранения сообщения;
  409 показывается существующей инлайн-подсказкой busyHint.
- Веб-тестов рендера/клика нет: в проекте нет компонентного тест-раннера
  (нет jest/vitest), вводить его ради одной карточки не стал (ub-mode).
  Покрытие: серверные тесты канала доставки + tsc/build.
- Предложение конспекта: запуск превью и так уже покрыт кнопками UI
  (быстрые действия «Фейнман/Закрепим/Конспект» + карточка превью с
  «Записать в базу»), offer_replies добавлен в местах, где агент сам
  спрашивает выбор (п.0.5/п.1.5/п.3 quick_reviewer, п.0.5/п.5 session_tutor).
- Финальную визуальную полировку карточки делает ZCode (скилл hallmark).
