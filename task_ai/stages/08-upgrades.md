## A. Понятия как отдельные сущности

**Зачем:** знание собирается вокруг идей, а не файлов. У понятия («Service», «инкапсуляция») своя страница: общее определение, определения из разных источников, блоки, где встречалось, расхождения между источниками. Позже на этом строится граф знаний.

### Модель

- Источник истины — MD-файл `kb/concepts/<slug>.md` (в git), индекс — SQLite.

````markdown
---
id: cpt_1a2b3c4d
term: Service
aliases: [k8s service, сервис kubernetes]
category: infra/kubernetes
created: 2026-10-20T10:00:00+03:00
updated: 2026-10-20T10:00:00+03:00
---

# Service

> Стабильная точка доступа к набору подов: постоянный IP/DNS-имя и балансировка, пока поды пересоздаются.

## Определения в источниках

- **Kubernetes in Action, гл. 3** — … ([[blk_87ab94]])
- **YouTube: …** — …

## Расхождения

- (если источники противоречат — что именно и где)
````

- Таблицы (модуль `knowledge`): `concepts(uid, slug, term, aliases_json, category_path, summary, path, created_at, updated_at)`, `block_concepts(block_uid, concept_uid, definition, PRIMARY KEY(block_uid, concept_uid))`, FTS по понятиям (`concepts_fts`).
- В frontmatter блока — опциональное поле `concepts: [cpt_…]`. В секции «Ключевые понятия» термин рендерится как ссылка `[[cpt_…|Термин]]`.
- `BlockDraft.concepts[*]` получает опциональное поле `concept_uid`.

### Задачи

- [x] Ревизия Alembic: таблицы понятий; `reindex` читает `kb/concepts/*.md` и связи из блоков.
- [x] Агент `concept_linker` (роль `fast`): для каждого понятия нового блока — найти существующее (по term/aliases + FTS-кандидаты в контексте) или создать новое; вход/выход — структурированный.
- [x] После сохранения блока (событие `BlockSaved`/`BlockUpdated`) — привязка понятий и пересборка страницы понятия: общее определение и «Расхождения» генерирует агент `concept_synthesizer` (роль `structured`) из всех определений понятия.
- [x] Бэкфилл: команда `cli backfill-concepts` проходит по существующим блокам.
- [x] Инструменты: `list_concepts(q?, category?)`, `get_concept(uid|slug)`; добавить их в `free_chat`, `quick_reviewer`, `session_tutor` — тьютор при объяснении понятия, которое уже есть в базе, опирается на его страницу и говорит «ты это уже встречал в …».
- [x] REST: `GET /api/kb/concepts`, `GET /api/kb/concepts/{slug}`.
- [x] Веб: `/kb/concepts` (алфавитный список с поиском и числом блоков), `/kb/concepts/[slug]` (общее определение, определения по источникам, расхождения — callout, блоки-чипы); кликабельные понятия на странице блока и в чате; ⌘K ищет понятия; экспорт (этап 6) включает понятия (`concepts/` в ZIP).

### Критерии приёмки

1. Тесты: линковка к существующему понятию по алиасу, создание нового, идемпотентность бэкфилла, пересборка страницы при новом блоке (FakeLLM), reindex из файлов.
2. Два блока из разных источников про одно понятие → одна страница понятия с двумя определениями; при намеренно противоречащих определениях заполнена секция «Расхождения».
3. Старые блоки без поля `concepts` открываются как раньше; после бэкфилла их понятия кликабельны.

## B. Цитаты на источник

**Зачем:** каждый тезис и определение в блоке указывает, откуда взят; клик открывает читалку на этом месте. Главная защита от выдумок модели.

### Модель

- Цитата: `{source, chapter, quote, start?, end?}`. Модель присылает только `quote` (точный фрагмент ≤ 200 символов); **смещения `start/end` вычисляет сервер** нечётким поиском фрагмента в тексте главы (нормализация пробелов/регистра, затем `difflib`/скользящее окно; порог совпадения — константа). Не нашёл — цитата сохраняется без смещений с пометкой `unresolved`.
- `BlockDraft`: опциональное поле `citations: list[Citation]` у тезиса и у понятия. Для совместимости тезис может быть строкой (старый формат) или объектом `{text, citations}`.
- Тезис без цитаты, если он из знаний агента, а не из источника, помечается `origin: agent` — в UI бейдж «вне книги».
- MD: сноски GFM. Тезис `- У каждого пода свой IP[^1]`, внизу блока `[^1]: Kubernetes in Action, гл. 3 — «…цитата…» (/library/src_…/3#c=1200-1350)`.
- Индекс: таблица `block_citations(block_uid, source_uid, chapter_idx, start, end, quote)`.

### Задачи

- [x] Тьюторы при `read_chapter` получают текст с явными границами порций; промпты `block_writer` и тьюторов требуют цитату к каждому тезису из источника и `origin: agent` для собственных дополнений.
- [x] Сервис разрешения цитат + ревизия Alembic для `block_citations`; сборка сносок в MD.
- [x] Читалка главы (этап 4): параметр `#c=start-end` прокручивает к фрагменту и подсвечивает его.
- [x] Страница блока: сноски кликабельны (hover-card с цитатой, клик → читалка), бейдж «вне книги»; на странице источника — счётчик цитат по главам.

### Критерии приёмки

1. Тесты: разрешение цитаты при точном совпадении, при отличиях в пробелах/регистре, отсутствие совпадения → `unresolved`; старый формат тезисов-строк валиден.
2. Новый урок по тестовой книге: ≥ 80% тезисов имеют разрешённые цитаты; клик по сноске открывает читалку с подсвеченным фрагментом.
3. Старые блоки без цитат рендерятся без ошибок.

## C. Ежедневное повторение через Telegram

**Зачем:** закрепление без захода на сайт — 2 минуты в день. Бот присылает вопрос по блокам с «Дозакрепить» и созревшим по интервалу, я отвечаю в Telegram, агент оценивает.

### Ограничения окружения (важно)

- На маке уже работает мост: LaunchAgent-демон `com.radmipa.telegram-bridge` — **единственный** поллер бота; входящие он пишет в SQLite `~/.config/opencode/telegram.db`. CLI: `python3 ~/.config/opencode/tools/telegram_bridge.py` (`send --to dmitry`, `unread --to dmitry`, `ack <update_id>`, `--parse-mode HTML`). Подробно — правило `~/.cursor/rules/telegram-bridge.mdc`.
- LearnOS **не опрашивает Telegram API сам** (второй поллер даёт 409) и не помечает прочитанными чужие сообщения: `ack` — только тех `update_id`, которые признаны ответом на вопрос повторения. `--consume` не использовать.
- Перед реализацией изучи `telegram_bridge.py` и схему `telegram.db` (только чтение): хранится ли `reply_to_message_id`, есть ли JSON-вывод у CLI. Выбранный способ запиши в «Отчёт».

### Модель и логика

- Новый модуль `review`: состояние повторения по блоку (`review_items(block_uid, ease, interval_days, due_at, last_quality, reps)`; поле `review` во frontmatter синхронизируется), алгоритм SM-2 в `domain.py` (чистые функции, полностью покрыты тестами).
- Очередь на день: сначала блоки со слабыми местами, затем созревшие по `due_at`; число вопросов в день и время — в профиле (`learning.review_daily_count`, по умолчанию 2; `learning.review_time`, по умолчанию `09:30`; `learning.review_enabled`).
- Агент `review_examiner` (роль `chat`): по блоку (+ его «Дозакрепить») формулирует один вопрос «объясни своими словами»; по ответу ставит качество 0–5, даёт короткую обратную связь и правильную формулировку. Слабые ответы добавляют пункт в «Дозакрепить» блока через `update_block`; устойчиво хорошие (качество ≥ 4 три раза подряд) — снимают соответствующий пункт.
- Порт `Messenger` (`send(text, html) -> message_id`, `poll_replies(since) -> list[Reply]`, `ack(update_id)`) и адаптер `TelegramBridgeMessenger` (subprocess CLI + чтение БД моста только на чтение). Тесты — на фейковом `Messenger`.
- Привязка ответа к вопросу: ответ — это reply на сообщение-вопрос (если мост хранит reply), иначе — первое текстовое сообщение от `dmitry` в окне 30 минут после вопроса. Команды в ответ: «ещё» — следующий вопрос, «пропусти» — отложить на завтра, «стоп» — выключить на сегодня.
- Планировщик — `asyncio`-задача в lifespan (как воркер jobs): срабатывает в `review_time`, если сервер запущен; пропущенное (мак спал) — отправляет при следующем старте, но не позже 21:00.
- Сообщение-вопрос: HTML, заголовок блока, вопрос, ссылка на блок (если задан `LEARNOS_PUBLIC_URL`, см. часть D).

### Задачи

- [x] Модуль `review` (домен SM-2, сервис, таблицы, события), агент `review_examiner`, порт `Messenger` + адаптер моста, планировщик.
- [x] Профиль: поля повторения; страница Настроек — включение, время, число вопросов, «Отправить вопрос сейчас» (для проверки).
- [x] Веб `/review`: те же вопросы в браузере (для дней, когда удобнее там) + история повторений и статистика по блокам; бейдж «к повторению: N» в сайдбаре.
- [x] Инструменты: `get_review_queue`, `answer_review` (тот же сценарий из любого MCP-клиента).

### Критерии приёмки

1. Тесты: SM-2 (интервалы при качестве 0–5), приоритет очереди, привязка ответа к вопросу (reply и окно), команды «ещё/пропусти/стоп», `ack` только своих сообщений, пропущенное окно отправки.
2. Живой сценарий: «Отправить вопрос сейчас» → вопрос пришёл в Telegram → ответ → оценка с обратной связью пришла в Telegram; `due_at` блока сдвинулся; при слабом ответе в блоке новый пункт «Дозакрепить» (версия +1).
3. Демон моста продолжает работать, другие входящие сообщения остаются непрочитанными (проверить `unread --to dmitry` до и после).

## E. Практика → готовая инструкция (runbook)

**Зачем:** после сессии с практикой, кроме урока, остаётся воспроизводимая инструкция «как я сделал X на своём железе» — команды, проверки, откат, грабли. Для DevOps это самый практичный артефакт.

### Модель

- Новый вид блока `kind: runbook` (тот же формат файла, `kb/blocks/`), двусторонняя связь с уроком (`links`).
- `practice_step` получает опциональные поля `verify` (проверочная команда) и `cleanup` (как откатить шаг). Тьютор заполняет `verify` для каждого шага, где результат можно проверить командой.
- Секции runbook: **Цель**, **Где** (машина из профиля + требования), **Предусловия**, **Шаги** (команда · что делает · проверка · ожидаемый результат), **Проверка итога**, **Откат / очистка**, **Грабли** (ошибки, встреченные в сессии, и как решили), **Связанный урок**.

### Задачи

- [x] Поля `verify`/`cleanup` в `practice_step` (опциональные) + обновить промпт `session_tutor`.
- [x] Агент `runbook_writer` (роль `structured`): из `practice_log` транскрипта, выводов пользователя и ошибок → `RunbookDraft`; запускается после `finish_session`, если в сессии ≥ 2 шагов практики с полученным выводом. В карточке `block_saved` — оба блока.
- [x] Рендер runbook на странице блока: шаги как `CommandCard` (копирование команды и проверки), режим «пройти заново» — чекбоксы шагов (состояние в localStorage), кнопка «Повторить с агентом» (сессия-практика по runbook в чате).
- [x] База знаний: фильтр по виду `runbook`, иконка `terminal-square`; экспорт включает runbook-и.
- [x] Инструмент `list_runbooks(machine?, q?)`; тьютор при новой практике на той же машине предлагает опереться на существующий runbook.

### Критерии приёмки

1. Тесты: генерация runbook на FakeLLM, порог «≥ 2 шагов с выводом», совместимость `practice_step` без новых полей.
2. Живая сессия с практикой на маке (например, поднять контейнер и проверить порт) → создано два блока: урок и runbook, связанные друг с другом; в runbook есть проверки и откат; режим «пройти заново» работает на телефоне.

## F. Повторы: «это ты уже знаешь»

**Зачем:** новый источник часто наполовину пересказывает то, что уже есть в базе. Агент должен это видеть и показывать: знакомое — коротким резюме со ссылкой на существующий блок («повтор»), а время сессии тратить на новое. Зависит от части A (понятия).

### Анализ покрытия

- `chapter_summarizer` (этап 2) получает опциональное поле выхода `concepts: [{term, gist}]` — понятия главы (до 15).
- Job **`analyze_coverage`** после summary глав (и пересчёт по событиям `BlockSaved`/`BlockUpdated` для затронутых понятий): для каждого понятия главы найти кандидатов в базе (понятия по term/aliases + FTS по блокам; если настроена роль `embed` — плюс семантическая близость) и решить агентом **`coverage_judge`** (роль `fast`), то же ли это понятие в том же смысле (контекст — категория и gist; «service» в Kubernetes ≠ «сервис» вообще). Новых понятий здесь не создаём — только сопоставление.
- Статус понятия главы:
  - `known` — есть блок-урок с этим понятием и оно не в «Дозакрепить»;
  - `weak` — есть, но в «Дозакрепить» или последнее повторение (часть C) было слабым;
  - `new` — в базе нет.
- Таблица `chapter_concepts(chapter_id, term, gist, concept_uid NULL, status, block_uids_json)`, поле `chapters.coverage_known_pct`. Источник целиком — агрегат по главам.

### Поведение агентов

- В контекст `quick_reviewer` и `session_tutor` добавляется покрытие текущей главы.
- **known** — не объяснять заново: 1–2 строки резюме + ссылка `[[blk_…]]` с пометкой «повтор: ты это проходил <дата>» + по желанию один короткий проверочный вопрос «напомни своими словами» (ответ идёт в повторение части C как сигнал качества).
- **weak** — объяснить заново с фокусом на записанном слабом месте.
- **new** — полноценное объяснение; бюджет теории сессии (`theory_concepts`) тратится в первую очередь на `new`.
- Если глава знакома на ≥ 80% — агент предлагает вместо полной сессии **«быстрый повтор»**: резюме знакомого со ссылками + 2–3 проверочных вопроса + только новое подробно.
- Если источник добавляет к знакомому понятию новый нюанс — агент явно говорит «в этой книге есть то, чего не было в твоём блоке: …».

### Блок после сессии/разбора

- Новая опциональная секция **«Уже знал»** (после «Связи»): ссылки на существующие блоки/понятия, которые встретились как повтор, и для каждого — что нового добавил этот источник (если добавил).
- `block_writer` не повторяет тезисы, которые уже есть в связанных блоках: знакомое — в «Уже знал», в «Тезисах» — только новое. Новые нюансы к знакомому понятию дописываются на страницу понятия (часть A), а не дублируются в блок.
- `BlockDraft`: опциональное поле `already_known: list[{ref: blk_…|cpt_…, added: str | None}]`.

### Инструменты, REST, UI

- Инструменты `get_chapter_coverage(source, chapter)`, `get_source_coverage(source)`; REST `GET /api/sources/{uid}/coverage`.
- Библиотека: на карточке источника — «новое ≈ 40%» (помогает решить, стоит ли читать); на странице источника у каждой главы — полоска покрытия и чипы понятий: зелёные (`known`, клик → блок), жёлтые (`weak`), синие (`new`); бейдж «Повтор» у глав с покрытием ≥ 70%.
- Чат: в правой панели сессии — «В этой главе: 5 новых, 3 знакомых, 1 слабое» со списком.
- Страница блока: секция «Уже знал» — чипы-ссылки с hover-card «что добавлено».

### Критерии приёмки

1. Тесты: статусы `known/weak/new`, отказ `coverage_judge` от омонимов (FakeLLM), пересчёт покрытия после нового блока, приоритет `new` в бюджете теории, секция «Уже знал» в round-trip MD, старые блоки без секции.
2. Живой сценарий: урок по главе 2 тестовой k8s-книги (поды, Service) → добавить YouTube-видео про Kubernetes Services → у видео покрытие показывает знакомые понятия со ссылками на блок; быстрый разбор видео: агент знакомое даёт резюме-повтором со ссылкой, подробно объясняет только новое; итоговый конспект содержит «Уже знал» и не повторяет тезисы исходного блока.

## A. Понятия как отдельные сущности

**Зачем:** знание собирается вокруг идей, а не файлов. У понятия («Service», «инкапсуляция») своя страница: общее определение, определения из разных источников, блоки, где встречалось, расхождения между источниками. Позже на этом строится граф знаний.

### Модель

- Источник истины — MD-файл `kb/concepts/<slug>.md` (в git), индекс — SQLite.

````markdown
---
id: cpt_1a2b3c4d
term: Service
aliases: [k8s service, сервис kubernetes]
category: infra/kubernetes
created: 2026-10-20T10:00:00+03:00
updated: 2026-10-20T10:00:00+03:00
---

# Service

> Стабильная точка доступа к набору подов: постоянный IP/DNS-имя и балансировка, пока поды пересоздаются.

## Определения в источниках

- **Kubernetes in Action, гл. 3** — … ([[blk_87ab94]])
- **YouTube: …** — …

## Расхождения

- (если источники противоречат — что именно и где)
````

- Таблицы (модуль `knowledge`): `concepts(uid, slug, term, aliases_json, category_path, summary, path, created_at, updated_at)`, `block_concepts(block_uid, concept_uid, definition, PRIMARY KEY(block_uid, concept_uid))`, FTS по понятиям (`concepts_fts`).
- В frontmatter блока — опциональное поле `concepts: [cpt_…]`. В секции «Ключевые понятия» термин рендерится как ссылка `[[cpt_…|Термин]]`.
- `BlockDraft.concepts[*]` получает опциональное поле `concept_uid`.

### Задачи

- [x] Ревизия Alembic: таблицы понятий; `reindex` читает `kb/concepts/*.md` и связи из блоков.
- [x] Агент `concept_linker` (роль `fast`): для каждого понятия нового блока — найти существующее (по term/aliases + FTS-кандидаты в контексте) или создать новое; вход/выход — структурированный.
- [x] После сохранения блока (событие `BlockSaved`/`BlockUpdated`) — привязка понятий и пересборка страницы понятия: общее определение и «Расхождения» генерирует агент `concept_synthesizer` (роль `structured`) из всех определений понятия.
- [x] Бэкфилл: команда `cli backfill-concepts` проходит по существующим блокам.
- [x] Инструменты: `list_concepts(q?, category?)`, `get_concept(uid|slug)`; добавить их в `free_chat`, `quick_reviewer`, `session_tutor` — тьютор при объяснении понятия, которое уже есть в базе, опирается на его страницу и говорит «ты это уже встречал в …».
- [x] REST: `GET /api/kb/concepts`, `GET /api/kb/concepts/{slug}`.
- [x] Веб: `/kb/concepts` (алфавитный список с поиском и числом блоков), `/kb/concepts/[slug]` (общее определение, определения по источникам, расхождения — callout, блоки-чипы); кликабельные понятия на странице блока и в чате; ⌘K ищет понятия; экспорт (этап 6) включает понятия (`concepts/` в ZIP).

## B. Цитаты на источник

**Зачем:** каждый тезис и определение в блоке указывает, откуда взят; клик открывает читалку на этом месте. Главная защита от выдумок модели.

### Модель

- Цитата: `{source, chapter, quote, start?, end?}`. Модель присылает только `quote` (точный фрагмент ≤ 200 символов); **смещения `start/end` вычисляет сервер** нечётким поиском фрагмента в тексте главы (нормализация пробелов/регистра, затем `difflib`/скользящее окно; порог совпадения — константа). Не нашёл — цитата сохраняется без смещений с пометкой `unresolved`.
- `BlockDraft`: опциональное поле `citations: list[Citation]` у тезиса и у понятия. Для совместимости тезис может быть строкой (старый формат) или объектом `{text, citations}`.
- Тезис без цитаты, если он из знаний агента, а не из источника, помечается `origin: agent` — в UI бейдж «вне книги».
- MD: сноски GFM. Тезис `- У каждого пода свой IP[^1]`, внизу блока `[^1]: Kubernetes in Action, гл. 3 — «…цитата…» (/library/src_…/3#c=1200-1350)`.
- Индекс: таблица `block_citations(block_uid, source_uid, chapter_idx, start, end, quote)`.

### Задачи

- [x] Тьюторы при `read_chapter` получают текст с явными границами порций; промпты `block_writer` и тьюторов требуют цитату к каждому тезису из источника и `origin: agent` для собственных дополнений.
- [x] Сервис разрешения цитат + ревизия Alembic для `block_citations`; сборка сносок в MD.
- [x] Читалка главы (этап 4): параметр `#c=start-end` прокручивает к фрагменту и подсвечивает его.
- [x] Страница блока: сноски кликабельны (hover-card с цитатой, клик → читалка), бейдж «вне книги»; на странице источника — счётчик цитат по главам.

### Критерии приёмки

1. Тесты: разрешение цитаты при точном совпадении, при отличиях в пробелах/регистре, отсутствие совпадения → `unresolved`; старый формат тезисов-строк валиден.
2. Новый урок по тестовой книге: ≥ 80% тезисов имеют разрешённые цитаты; клик по сноске открывает читалку с подсвеченным фрагментом.
3. Старые блоки без цитат рендерятся без ошибок.

## C. Ежедневное повторение через Telegram

**Зачем:** закрепление без захода на сайт — 2 минуты в день. Бот присылает вопрос по блокам с «Дозакрепить» и созревшим по интервалу, я отвечаю в Telegram, агент оценивает.

### Ограничения окружения (важно)

- На маке уже работает мост: LaunchAgent-демон `com.radmipa.telegram-bridge` — **единственный** поллер бота; входящие он пишет в SQLite `~/.config/opencode/telegram.db`. CLI: `python3 ~/.config/opencode/tools/telegram_bridge.py` (`send --to dmitry`, `unread --to dmitry`, `ack <update_id>`, `--parse-mode HTML`). Подробно — правило `~/.cursor/rules/telegram-bridge.mdc`.
- LearnOS **не опрашивает Telegram API сам** (второй поллер даёт 409) и не помечает прочитанными чужие сообщения: `ack` — только тех `update_id`, которые признаны ответом на вопрос повторения. `--consume` не использовать.
- Перед реализацией изучи `telegram_bridge.py` и схему `telegram.db` (только чтение): хранится ли `reply_to_message_id`, есть ли JSON-вывод у CLI. Выбранный способ запиши в «Отчёт».

### Модель и логика

- Новый модуль `review`: состояние повторения по блоку (`review_items(block_uid, ease, interval_days, due_at, last_quality, reps)`; поле `review` во frontmatter синхронизируется), алгоритм SM-2 в `domain.py` (чистые функции, полностью покрыты тестами).
- Очередь на день: сначала блоки со слабыми местами, затем созревшие по `due_at`; число вопросов в день и время — в профиле (`learning.review_daily_count`, по умолчанию 2; `learning.review_time`, по умолчанию `09:30`; `learning.review_enabled`).
- Агент `review_examiner` (роль `chat`): по блоку (+ его «Дозакрепить») формулирует один вопрос «объясни своими словами»; по ответу ставит качество 0–5, даёт короткую обратную связь и правильную формулировку. Слабые ответы добавляют пункт в «Дозакрепить» блока через `update_block`; устойчиво хорошие (качество ≥ 4 три раза подряд) — снимают соответствующий пункт.
- Порт `Messenger` (`send(text, html) -> message_id`, `poll_replies(since) -> list[Reply]`, `ack(update_id)`) и адаптер `TelegramBridgeMessenger` (subprocess CLI + чтение БД моста только на чтение). Тесты — на фейковом `Messenger`.
- Привязка ответа к вопросу: ответ — это reply на сообщение-вопрос (если мост хранит reply), иначе — первое текстовое сообщение от `dmitry` в окне 30 минут после вопроса. Команды в ответ: «ещё» — следующий вопрос, «пропусти» — отложить на завтра, «стоп» — выключить на сегодня.
- Планировщик — `asyncio`-задача в lifespan (как воркер jobs): срабатывает в `review_time`, если сервер запущен; пропущенное (мак спал) — отправляет при следующем старте, но не позже 21:00.
- Сообщение-вопрос: HTML, заголовок блока, вопрос, ссылка на блок (если задан `LEARNOS_PUBLIC_URL`, см. часть D).

### Задачи

- [x] Модуль `review` (домен SM-2, сервис, таблицы, события), агент `review_examiner`, порт `Messenger` + адаптер моста, планировщик.
- [x] Профиль: поля повторения; страница Настроек — включение, время, число вопросов, «Отправить вопрос сейчас» (для проверки).
- [x] Веб `/review`: те же вопросы в браузере (для дней, когда удобнее там) + история повторений и статистика по блокам; бейдж «к повторению: N» в сайдбаре.
- [x] Инструменты: `get_review_queue`, `answer_review` (тот же сценарий из любого MCP-клиента).

### Критерии приёмки

1. Тесты: SM-2 (интервалы при качестве 0–5), приоритет очереди, привязка ответа к вопросу (reply и окно), команды «ещё/пропусти/стоп», `ack` только своих сообщений, пропущенное окно отправки.
2. Живой сценарий: «Отправить вопрос сейчас» → вопрос пришёл в Telegram → ответ → оценка с обратной связью пришла в Telegram; `due_at` блока сдвинулся; при слабом ответе в блоке новый пункт «Дозакрепить» (версия +1).
3. Демон моста продолжает работать, другие входящие сообщения остаются непрочитанными (проверить `unread --to dmitry` до и после).

## E. Практика → готовая инструкция (runbook)

**Зачем:** после сессии с практикой, кроме урока, остаётся воспроизводимая инструкция «как я сделал X на своём железе» — команды, проверки, откат, грабли. Для DevOps это самый практичный артефакт.

### Модель

- Новый вид блока `kind: runbook` (тот же формат файла, `kb/blocks/`), двусторонняя связь с уроком (`links`).
- `practice_step` получает опциональные поля `verify` (проверочная команда) и `cleanup` (как откатить шаг). Тьютор заполняет `verify` для каждого шага, где результат можно проверить командой.
- Секции runbook: **Цель**, **Где** (машина из профиля + требования), **Предусловия**, **Шаги** (команда · что делает · проверка · ожидаемый результат), **Проверка итога**, **Откат / очистка**, **Грабли** (ошибки, встреченные в сессии, и как решили), **Связанный урок**.

### Задачи

- [x] Поля `verify`/`cleanup` в `practice_step` (опциональные) + обновить промпт `session_tutor`.
- [x] Агент `runbook_writer` (роль `structured`): из `practice_log` транскрипта, выводов пользователя и ошибок → `RunbookDraft`; запускается после `finish_session`, если в сессии ≥ 2 шагов практики с полученным выводом. В карточке `block_saved` — оба блока.
- [x] Рендер runbook на странице блока: шаги как `CommandCard` (копирование команды и проверки), режим «пройти заново» — чекбоксы шагов (состояние в localStorage), кнопка «Повторить с агентом» (сессия-практика по runbook в чате).
- [x] База знаний: фильтр по виду `runbook`, иконка `terminal-square`; экспорт включает runbook-и.
- [x] Инструмент `list_runbooks(machine?, q?)`; тьютор при новой практике на той же машине предлагает опереться на существующий runbook.

### Критерии приёмки

1. Тесты: генерация runbook на FakeLLM, порог «≥ 2 шагов с выводом», совместимость `practice_step` без новых полей.
2. Живая сессия с практикой на маке (например, поднять контейнер и проверить порт) → создано два блока: урок и runbook, связанные друг с другом; в runbook есть проверки и откат; режим «пройти заново» работает на телефоне.

## F. Повторы: «это ты уже знаешь»

**Зачем:** новый источник часто наполовину пересказывает то, что уже есть в базе. Агент должен это видеть и показывать: знакомое — коротким резюме со ссылкой на существующий блок («повтор»), а время сессии тратить на новое. Зависит от части A (понятия).

### Анализ покрытия

- `chapter_summarizer` (этап 2) получает опциональное поле выхода `concepts: [{term, gist}]` — понятия главы (до 15).
- Job **`analyze_coverage`** после summary глав (и пересчёт по событиям `BlockSaved`/`BlockUpdated` для затронутых понятий): для каждого понятия главы найти кандидатов в базе (понятия по term/aliases + FTS по блокам; если настроена роль `embed` — плюс семантическая близость) и решить агентом **`coverage_judge`** (роль `fast`), то же ли это понятие в том же смысле (контекст — категория и gist; «service» в Kubernetes ≠ «сервис» вообще). Новых понятий здесь не создаём — только сопоставление.
- Статус понятия главы:
  - `known` — есть блок-урок с этим понятием и оно не в «Дозакрепить»;
  - `weak` — есть, но в «Дозакрепить» или последнее повторение (часть C) было слабым;
  - `new` — в базе нет.
- Таблица `chapter_concepts(chapter_id, term, gist, concept_uid NULL, status, block_uids_json)`, поле `chapters.coverage_known_pct`. Источник целиком — агрегат по главам.

### Поведение агентов

- В контекст `quick_reviewer` и `session_tutor` добавляется покрытие текущей главы.
- **known** — не объяснять заново: 1–2 строки резюме + ссылка `[[blk_…]]` с пометкой «повтор: ты это проходил <дата>» + по желанию один короткий проверочный вопрос «напомни своими словами» (ответ идёт в повторение части C как сигнал качества).
- **weak** — объяснить заново с фокусом на записанном слабом месте.
- **new** — полноценное объяснение; бюджет теории сессии (`theory_concepts`) тратится в первую очередь на `new`.
- Если глава знакома на ≥ 80% — агент предлагает вместо полной сессии **«быстрый повтор»**: резюме знакомого со ссылками + 2–3 проверочных вопроса + только новое подробно.
- Если источник добавляет к знакомому понятию новый нюанс — агент явно говорит «в этой книге есть то, чего не было в твоём блоке: …».

### Блок после сессии/разбора

- Новая опциональная секция **«Уже знал»** (после «Связи»): ссылки на существующие блоки/понятия, которые встретились как повтор, и для каждого — что нового добавил этот источник (если добавил).
- `block_writer` не повторяет тезисы, которые уже есть в связанных блоках: знакомое — в «Уже знал», в «Тезисах» — только новое. Новые нюансы к знакомому понятию дописываются на страницу понятия (часть A), а не дублируются в блок.
- `BlockDraft`: опциональное поле `already_known: list[{ref: blk_…|cpt_…, added: str | None}]`.

### Инструменты, REST, UI

- Инструменты `get_chapter_coverage(source, chapter)`, `get_source_coverage(source)`; REST `GET /api/sources/{uid}/coverage`.
- Библиотека: на карточке источника — «новое ≈ 40%» (помогает решить, стоит ли читать); на странице источника у каждой главы — полоска покрытия и чипы понятий: зелёные (`known`, клик → блок), жёлтые (`weak`), синие (`new`); бейдж «Повтор» у глав с покрытием ≥ 70%.
- Чат: в правой панели сессии — «В этой главе: 5 новых, 3 знакомых, 1 слабое» со списком.
- Страница блока: секция «Уже знал» — чипы-ссылки с hover-card «что добавлено».

### Критерии приёмки

1. Тесты: статусы `known/weak/new`, отказ `coverage_judge` от омонимов (FakeLLM), пересчёт покрытия после нового блока, приоритет `new` в бюджете теории, секция «Уже знал» в round-trip MD, старые блоки без секции.
2. Живой сценарий: урок по главе 2 тестовой k8s-книги (поды, Service) → добавить YouTube-видео про Kubernetes Services → у видео покрытие показывает знакомые понятия со ссылками на блок; быстрый разбор видео: агент знакомое даёт резюме-повтором со ссылкой, подробно объясняет только новое; итоговый конспект содержит «Уже знал» и не повторяет тезисы исходного блока.
3. Глава, знакомая на ≥ 80%, — агент предлагает «быстрый повтор».
