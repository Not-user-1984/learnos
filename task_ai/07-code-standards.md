# 07 — Правила кода и тестов

Цель — код, который читается с первого раза, легко тестируется и выдержит рост до прод-версии. Пиши минимально достаточный код: решай задачу этапа, а не гипотетические будущие. **Мало кода, гибко, понятно** — лучше меньше функций, чем больше лишних: каждая новая функция, слой или параметр должны оправдывать себя здесь и сейчас, а не «на вырост».

## Принципы ub-mode (обязательны при написании и правке кода)

Приняты 2026-10-28 из [unclebob/ub-mode](https://github.com/unclebob/ub-mode). Полный перевод с оригиналом — [reference/ub-mode-ru.md](reference/ub-mode-ru.md). Каждое изменение кода проходит три фазы.

**Фаза 1 — сначала заставь работать:**

- **Протокол лени**: одно решение живёт в одном месте; поставь минимальную правку, которая решает проблему.
- **Фундаментальное мышление**: сначала правильная форма данных, потом логика; делай раньше то, что поможет всем следующим фазам.
- **TDD**: падающий тест до правки кода; убедись, что падает по ожидаемой причине; минимальное изменение, чтобы прошёл. Если честный тест нецелесообразен — не пиши плохой вместо него.
- **Перепроектируй с первых принципов**: не прикручивай новое требование к старому дизайну — спроси, что построил бы, если бы оно было с самого начала, и доставляй кусками.
- **Атакуй предпосылку**: два фикса на одной предпосылке валятся об один шлюз → запиши предпосылку предложением и убери сам перекос, до новых фиксов.
- **Сначала вычти, потом добавляй**: убирай сложность до того, как добавлять.
- **Построй рычаг**: работу, которую не видишь с одного взгляда, делай инструментом; одну единицу руками, потом инструмент повторяет её.
- **Архитектура**: невозможные состояния сделай невыразимыми; данные проверяются на входе, внутри — доверие; бизнес-логика — чистые функции; не заглушай компилятор; операции идемпотентны (два запуска = один результат); у изменяемого состояния один писатель.

**Фаза 2 — потом сделай правильным:**

- **Корневая причина**: воспроизведи → почини причину; страж, прячущий падение, — не фикс.
- **Проверяемые единицы**: заверши малую единицу, проверь, потом следующая.
- **Тестируй поведение, а не реализацию**: тест зовёт код как пользователь и проверяет видимый пользователю результат; тест, зелёный при пустых функциях, — выбросить.
- Гейты качества (замена crapper/dryer/mutator из оригинала): `ruff` + `mypy` + `lint-imports` + `pytest` зелёные; заметный дубль и функция-громоздина режутся там же, не «потом»; мёртвый код удаляется.

**Фаза 3 — следуй практике:**

- **Журнал**: записывай действия и причины; в отчёте — что и зачем сделано.
- **Береги окно контекста**: главное — маленьким; основную массу — в субагентов/файлы, себе — саммари.
- **Коммить и пушь**: часто, маленькими упорядоченными коммитами; каждый говорит «почему, что, чем доказано».

Эти принципы не отменяют разделы ниже (стиль, слои, тесты) — они задают порядок принятия решений, когда требований несколько.

## Правило пропорциональности

Слои и абстракции из [02-architecture.md](02-architecture.md) — инструмент, а не обязательный ритуал. Церемонию вводи, только когда она окупается:

- **Порт (`Protocol`)** — только для внешнего мира, который подменяется в тестах или имеет несколько реализаций: LLM, файлы KB, время/id, мессенджер, скиллы, рендер. Для собственной SQLite-таблицы отдельный порт не нужен — репозиторий и есть граница.
- **Простые модули** (profile, settings, export и подобный CRUD) — плоско: `service.py` + `api.py` + `tools.py` + таблицы, без `domain.py` и доменных dataclass, пока в модуле нет правил сложнее «прочитать/записать». Разрастётся — разнесёшь по слоям.
- **UnitOfWork** — там, где одна операция пишет в несколько мест (MD-файл + индекс + версия). Одиночное чтение/запись — без него.
- **Шина событий** — только для реальных межмодульных реакций (блок сохранён → понятия, повторение). Не превращай вызов внутри модуля в событие.
- Не плоди файлы «на вырост»: пустые `domain.py`, `ports.py`, `events.py` не создавай.
- Не переделывай уже написанный код ради этого правила — оно для нового кода и для случаев, когда ты всё равно трогаешь модуль.

## Общее

- Идентификаторы (имена переменных, классов, файлов) — на английском. Тексты UI, сообщения ошибок для пользователя, промпты, docstring и комментарии — на русском.
- Одна ответственность на функцию/класс. Функция длиннее ~40 строк — сигнал разделить.
- Нет мёртвого кода, закомментированных кусков, `print`, TODO без задачи в файле этапа.
- Комментарий в коде объясняет **ограничение или неочевидную причину** («z.ai не поддерживает json_schema — валидируем сами»), а не пересказывает строку.
- Магические числа и строки — в константы или `Settings`.
- Секреты — только из env через `Settings`; не логировать, не писать в файлы, не возвращать из API.

## Python (server/)

### Стиль и инструменты

- Python 3.12, полная аннотация типов. `ruff` (lint + format, line-length 110), `mypy --strict` для `app/kernel`, `app/llm`, `app/agent`, `app/modules/*/domain.py`, `service.py`; остальное — обычный `mypy`.
- Команда проверки (добавить в `pyproject.toml` как скрипты или `Makefile`):

```bash
uv run ruff check . && uv run ruff format --check . && uv run mypy app && uv run lint-imports && uv run pytest
```

### Docstring — на русском, коротко

Обязательны у каждого модуля (файла), публичного класса, публичной функции/метода, `Protocol`. Одна строка — что это и зачем; дальше — только если есть неочевидное (инварианты, побочные эффекты, исключения). Аргументы описываем, только когда имя и тип не говорят всё сами.

```python
"""Сервис базы знаний: сохранение, правка и версионирование блоков."""


class KnowledgeService:
    """Use-cases базы знаний. Блок всегда пишется в MD-файл и в индекс в одной операции."""

    def __init__(self, uow: UnitOfWorkFactory, files: BlockFileStore, ids: IdGenerator, clock: Clock) -> None:
        self._uow = uow
        self._files = files
        self._ids = ids
        self._clock = clock

    def update_block(self, uid: str, patch: BlockPatch, reason: str, conversation_uid: str | None) -> Block:
        """Применяет правку к блоку сразу и сохраняет предыдущую версию.

        Raises:
            NotFound: блока с таким uid нет.
        """
        with self._uow() as uow:
            block = uow.blocks.get(uid)
            uow.versions.add(block.snapshot(reason=reason, conversation_uid=conversation_uid))
            updated = block.apply(patch, now=self._clock.now())
            self._files.write(updated)
            uow.blocks.save(updated)
            uow.emit(BlockUpdated(uid=uid, version=updated.version))
            return updated
```

### Слои (см. 02-architecture.md)

- **domain:** `@dataclass(slots=True)` (frozen, где можно), чистые функции и методы с правилами. Никаких импортов FastAPI, SQLAlchemy, pydantic, openai, файловой системы. Время и id передаются параметрами.
- **ports:** `typing.Protocol`, по одному на внешнюю зависимость.
- **service:** оркестрация use-case: UoW, вызов домена, портов, событий, агентов. Не знает про HTTP и MCP.
- **infra:** реализация портов. Маппинг строк БД ↔ доменные объекты — здесь.
- **api.py / tools.py:** 3–10 строк на обработчик: DTO → сервис → DTO. Без бизнес-логики и SQL.
- Pydantic — только на границах (`schemas.py`, конфиг, LLM-структуры). Внутри — доменные dataclass.

### Ошибки

- Иерархия в `kernel/errors.py`: `AppError(code, message)` → `NotFound`, `Conflict`, `InvalidState` (например, неверный переход сессии), `ValidationFailed`, `ExternalServiceError`, `LLMError`.
- Домен и сервисы бросают их; REST-слой маппит в HTTP (404/409/422/502) одним exception handler; адаптер инструментов — в `{"error", "message"}`.
- Голый `except Exception` — только на внешних границах (воркер jobs, цикл агента) с логированием и переводом в `AppError`.

### Зависимости и тестируемость

- Внешний мир (время, id, LLM, файлы, сеть, скиллы) — через порты, внедряются в конструктор. Никаких глобальных синглтонов и импорта `settings` внутри функций домена/сервиса.
- Сборка зависимостей — только в `bootstrap.py` и тестовых фикстурах.

## Тесты

| Уровень | Папка | Что | Чем |
|---|---|---|---|
| unit | `tests/unit/<module>/` | домен (стейт-машина сессии, патч блока, сборка MD из `BlockDraft`, разбор frontmatter), сервисы с фейковыми портами | pytest, без БД и сети |
| integration | `tests/integration/` | SQL-репозитории на tmp SQLite, MD-хранилище на `tmp_path`, миграции Alembic (включая перенос v1 → v2 на фикстуре старой БД), reindex | pytest |
| api | `tests/api/` | REST и SSE через `httpx.AsyncClient`/`TestClient`, приложение с `FakeLLMProvider` | pytest-asyncio |
| contract | `tests/contract/` | каждый инструмент реестра: схема валидна, имя уникально, старые MCP-имена на месте; снапшот OpenAPI | pytest |
| agent | `tests/agent/` | `AgentRuntime` со сценарным `FakeLLMProvider`: текст, tool call → результат → финал, max_steps, отмена, неизвестный инструмент | pytest-asyncio |

Правила:

- Тест называется по поведению: `test_finish_session_rejected_outside_debrief`.
- Arrange / Act / Assert, один сценарий на тест; фабрики тестовых данных в `tests/factories.py`.
- Сеть в тестах выключена; реальный LLM — только `uv run python -m app.cli smoke-llm` (вручную, через `sec exec`).
- Каждый найденный баг — сначала падающий тест, потом фикс.
- Процент покрытия не гоняем. Обязательны тесты на то, что дорого сломать: стейт-машина сессии, сборка и разбор MD-блока (round-trip), правки и откаты версий, миграции и `reindex`, контракт паритета MCP, цикл `AgentRuntime`. Простой CRUD покрывается api-тестом «счастливого пути» и одной ошибкой.

## TypeScript (web/)

- `strict: true`, без `any` и `as`-приведений к непроверенным данным (внешние данные — через типы OpenAPI или zod).
- Server Components по умолчанию; `"use client"` — только в листьях с интерактивом.
- Структура: `src/app/` (роуты), `src/components/ui/` (shadcn, правим как свой код), `src/components/<feature>/` (chat, kb, library, courses, settings, markdown), `src/lib/` (api-клиент, chat-стрим, утилиты), `src/types/api.ts` (генерируется, руками не править).
- Компонент — один файл, ≤ ~150 строк; больше — выносить подкомпоненты/хуки.
- JSDoc на русском — у хуков, функций `lib/` и нетривиальных компонентов: одна строка «что и зачем».
- Стили — Tailwind-классы и токены темы shadcn; свои цвета — только через CSS-переменные в `globals.css`.
- Проверка этапа: `npm run lint && npx tsc --noEmit && npm run build`.
