# Архитектура CI/CD и деплоя LearnOS (2026-11-01)

Документ описывает путь кода от коммита на маке до работающего прода на CT 132.
Назначение — ревизия адекватности подхода: все решения, компромиссы и известные
ограничения перечислены явно. Формулировки «из аудита» — пункты внешнего аудита
[audit-2026-11-01.md](audit-2026-11-01.md) (раздел G / R-21).

## 1. Контекст и ограничения, в которых выбрана схема

- Персональный продукт, один разработчик, **один прод-стенд**: Proxmox CT 132
  `learnos` (4c/6G), docker compose внутри CT (server, web, xray-sidecar).
- Разработка на маке; режим работы — автономный агент (код → тесты → push →
  деплой без подтверждений), поэтому «деплой = git push» — ядро воркфлоу.
- Репозитории-зеркала: **GitHub** `Not-user-1984/learnos` (основной, с него
  тянет прод) и **GitVerse** `NotUser1984/learnos`. На маке один remote `origin`
  с двумя pushurl — `git push` уходит в оба одновременно.
- Хом-сервер спит 19:00–08:30 (systemd homelab-sleep) — ночных окон деплоя нет.

## 2. Поток кода (главная схема)

```
┌────────── мак (разработка) ──────────┐
│ uv run ruff/lint-imports/pytest      │  локальный прогон перед коммитом
│ cd web && npm lint/tsc/build          │
│ git push origin main                  │  один пуш → оба зеркала
└───────────────┬──────────────────────┘
                │ (только git-исходники, сотни КБ)
      ┌─────────┴──────────┐
      ▼                    ▼
┌─ GitHub (основное) ┐  ┌─ GitVerse (зеркало) ─┐
│ Actions: CI        │  │ хранит копию,        │
│ server: ruff+      │  │ CI не настроен       │
│  lint-imports+     │  └──────────────────────┘
│  pytest (361)      │
│ web: eslint+tsc+   │   сигнальный слой: статус ≤3 мин,
│  build             │   артефактов не создаёт
└─────────┬──────────┘
          │ git fetch (таймер learnos-deploy.timer, раз в 2 мин)
          ▼
┌─ CT 132 (прод, всё локально) ─────────────────────────────────┐
│ 1. fetch → есть новые коммиты? нет → выход                     │
│ 2. git reset --hard origin/main                                │
│ 3. docker compose build --pull  ← ОБРАЗ СОБИРАЕТСЯ ЗДЕСЬ,      │
│                                     из кэша слоёв (~40 cек)    │
│ 4. CI-ГЕЙТ: docker compose run --rm (одноразовый контейнер     │
│    из свежего образа): ruff check + lint-imports + pytest      │
│    (~2.5 мин; env чистый: /tmp-каталоги, без API-токена;       │
│    revision-тесты скип — в образе нет git)                     │
│ 5. зелёно → docker compose up -d → health-check /api/health    │
│    (30×5с; health — единственный открытый эндпоинт)            │
│ 6. падение на 2–4 → откат рабочей копии на прежний коммит,     │
│    контейнеры остаются на старом образе, таймер ретраит        │
└────────────────────────────────────────────────────────────────┘
```

**Образ никуда не передаётся**: registry нет, по сети едут только исходники.
Прод-образ существует в одном экземпляре — на CT (плюс локальные build-кэши
на маке при разработке).

## 3. Почему два прогона одних и тех же тестов

| | GitHub Actions | Гейт на CT |
|---|---|---|
| Что | тот же pytest/ruff + веб | ruff + pytest (без веба) |
| Когда | ≤3 мин после пуша | в момент деплоя |
| Что гарантирует | обратная связь разработчику | прод физически не принимает красный коммит |
| От чего зависит | от GitHub (внешний сервис) | ни от чего внешнего |

Дублирование осознанное: Actions может лежать/быть недоступным (или красный
коммит запушат в обход) — гейт на проде не зависит от внешних сервисов.
Веб (eslint/tsc/build) в гейт не включён: node-сборка на CT дорогая (место,
время, качает node_modules); её закрывает Actions и локальный прогон.
Известный зазор: упавший только веб-билд Actions поймает, гейт — нет.

## 4. Образы и секреты

- `server/Dockerfile`: python:3.12-slim + uv; зависимости ставятся на сборке
  (`uv sync --frozen --no-dev`), тесты копируются в образ (нужны гейту),
  CMD `uv run --frozen --no-dev uvicorn` — старт не тянет dev-группу.
  Dev-зависимости ставятся только внутри одноразового гейт-контейнера.
- `server/.dockerignore`: кэши исключены, `tests/` — включены (компромисс:
  тесты в прод-образе, ~100 КБ).
- Секреты: на CT `/opt/learnos/.env` (chmod 600: ZAI_API_KEY*, Telegram,
  Tavily/Serper, LEARNOS_API_TOKEN — bearer для /api и /mcp); на маке —
  Keychain через `sec`. В git секретов нет.
- `/repo` (рабочая копия ro для агента-аудитора): `.env` и `data/` замаскированы
  пустыми bind-mount (R-06 аудита).
- `/api/health` — единственный эндпоинт без токена (нужен самому деплою);
  остальной API и MCP за `Authorization: Bearer`.

## 5. Принятые компромиссы (для проверки адекватности)

1. **Нет registry, сборка на проде.** Плюсы: нет прокачки сотен МБ, нет ещё
   одной учётки/токена, инкрементальный кэш слоёв делает build ~40 сек, схема
   работает при недоступном GitHub Actions. Минусы: тратит CPU CT (build+тесты
   на проде каждые 2 мин при красном main), нет «золотых» артефактов
   (невозможен откат на образ — только на коммит с пересборкой), при поломанном
   Dockerfile на CT падает build (прод остаётся на старом — ок).
2. **Ретраи без backoff:** пока в main красный коммит, таймер каждые 2 мин
   повторяет build+гейт (~3 мин работы). Проду не вредит (flock, контейнеры на
   старом), но грузит CT и лог. Кандидат на backoff/степ-фактор.
3. **Деплой только из main, без PR-гейтов.** Осознанно: solo-разработка +
   автономный агент. Actions запускается и на PR — если появится практика PR,
   гейты уже описаны.
4. **Откат = git reset к предыдущему коммиту, контейнеры не трогаются.**
   Старый образ остаётся на CT как dangling до чистки; откат «на образ» не
   автоматизирован (в T-052).
5. **Здоровье прода = /api/health 200.** Deep-проверки (миграции прошли,
   воркер жив, LLM отвечает) не входят; worker_running, например, не отличает
   живую петлю от зависшей (T-033).
6. **GitVerse — пассивное зеркало** (CI там не настроен; формат Actions
   совместим, файл .github/workflows/ci.yml в репо уже лежит — при желании
   включается раннерами GitVerse). Одиночная точка свежести — GitHub: если
   зеркала разойдутся, прод тянет с GitHub.

## 6. Чего сознательно ещё нет (бэклог T-052, раздел G аудита)

- бэкапы SQLite (`sqlite3 .backup`) перед миграцией и по расписанию + копия kb/;
- healthcheck в compose (`depends_on: condition: service_healthy`);
- миграции fail-fast (сейчас тихий fallback на `create_all` — R-21);
- пины версий базовых образов (uv:latest, xray:latest, deno по ARG — фикс);
- сервер в контейнере работает от root;
- `kb/` — отдельный приватный git-репо с авто-коммитами (сейчас в основном
  репо, и `reset --hard` на CT может откатывать ручные правки категорий);
- CI-статус как обязательный гейт merge (нет merge-политики).
