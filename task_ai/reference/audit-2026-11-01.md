Нумерация `R-xx` намеренно отличается от реестра `task_ai/bugs/BUG-xxx`.

## Как работать с этим отчётом (инструкция для исполняющей нейронки)

- Правила проекта: `AGENTS.md`, `task_ai/07-code-standards.md` (русские docstring, слои domain→service→infra, новое поведение = тесты).
- Проверки перед коммитом: `cd server && uv run ruff check . && uv run ruff format --check . && uv run lint-imports && uv run pytest`; `cd web && npm run lint && npx tsc --noEmit && npm run build`.
- Порядок: **P0 → P1 → P2**. Один пункт = один коммит + тест, воспроизводящий баг ДО фикса (red → green).
- Файлы из guard-листа (`bootstrap.py`, `main.py`, `llm/`, `web/`, `docker-compose*`) агент-аудитор менять не может — их правит человек/dev-агент.
- Цель продукта (важно для приоритетов): учебный harness, где **знание рождается через понимание**. Всё, что молча теряет/портит знание или создаёт иллюзию «агент всё прочитал», — P0.

## P0 — чинить первым

### R-01 Обрезка tool-результатов ломает чтение источников [подтв.]
**Где:** `server/app/kernel/tools/registry.py::_truncate`, `server/app/modules/library/service.py::read_chapter`, `research/tools.py::web_read`, `research/service.py::window`.
**Что:** для канала `agent` результат режется до `tool_result_max_chars=8000`. `_truncate` обрезает каждое строковое поле до `max_chars//2 = 4000` символов. Но `read_chapter` по умолчанию отдаёт окно `limit=12000` и считает `next_offset = offset+limit`. Итог: агент получает первые 4000 из 12000 символов, а `next_offset` перепрыгивает остальные 8000. Промпт `quick_reviewer` для видео требует `limit=24000` и «листай до next_offset=null» — агент увидит ~17% транскрипта и будет уверен, что прочитал всё. Разбор главы строится на 1/3 текста.
Вторая часть: списки оборачиваются в `{"result": [...]}`; если `len(str(list)) ≥ 4000`, поле **выбрасывается целиком** и остаётся `{"truncated": true}`. Так ломаются `list_blocks`, `list_chapters`, `get_source` (chapters), `search`, `list_sources` на реальных объёмах — агент решает, что данных нет.
**Фикс:**
1. Не режем «оконные» ответы: у `ToolSpec` добавить `max_result_chars: int | None` (override), для `read_chapter`/`web_read` — окно по умолчанию ≤ 6000 и truncate отключён; либо `_truncate` корректирует `next_offset` под фактически отданный кусок.
2. Для списков — режем по элементам (первые N + `"more": K`) с явным флагом и подсказкой агенту (`"truncated_items": K, "hint": "уточни фильтр"`).
3. В промптах (`quick_reviewer`, `root`) убрать «limit=24000» и описать «читай окнами по next_offset».
**Тест:** `read_chapter` на главе 30k символов через `registry.call(..., channel="agent")`: суммарно по окнам агент получает все 30k без дыр; `list_blocks` на 100 блоках возвращает ≥ первые N элементов, а не `{"truncated":true}`. Существующий `test_truncate_*` не проверяет согласованность с offset — дополнить.

### R-02 `update_block` портит блок [подтв.]
**Где:** `server/app/modules/knowledge/service.py::_draft_from_frontmatter`, `::_section_items`, `::update_block`, `domain.py::draft_to_markdown`.
**Что (три независимых дефекта):**
1. `_draft_from_frontmatter` собирает `BlockDraft` **без `concepts` и `practice`** → после любой правки (`append_theses`, ответ в повторении) секции «Ключевые понятия» и «Практика» исчезают из файла (остаётся только в `block_versions`).
2. «Дозакрепить»: рендерится как `> [!WARNING]\n> текст`; парсер читает каждую строку блок-цитаты как пункт → получаются пункты `"[!WARNING]"` и `"текст"`; при пересборке каждый становится новым callout. Количество растёт при каждой правке, `weak_spots_count` врёт, очередь повторений раздувается. Дополнительно подряд идущие callout'ы без пустой строки сливаются в один при рендере.
3. `draft_to_markdown` всегда пишет `category_status: suggested`. БД держит `confirmed` (так сохраняет `save_note`/`finish_session`), файл — `suggested`. «Файл — источник истины», поэтому `reindex` (кнопка в настройках) возвращает все блоки во «Входящие».
Усугубляет: `ReviewService.answer` при `quality<3` сам вызывает `update_block` → каждый слабый ответ портит блок.
**Фикс:** парсить markdown ↔ драфт без потерь (или хранить канонический JSON-драфт в frontmatter/рядом и рендерить из него); писать `category_status` из `meta`, а не константой; callout'ы разделять пустой строкой и парсить по `> [!WARNING]` как маркеру, а не по строкам. Лучший вариант: `update_block` оперирует структурой (JSON-sidecar `kb/blocks/<stem>.json`), MD — только рендер.
**Тест (service-level, сейчас его нет):** save_block с concepts+practice+2 weak_spots → `update_block(append_theses)` → concepts/practice на месте, weak_spots == 2, `category_status` в файле == `confirmed`; затем `reindex()` не меняет статус.

### R-03 `finish_session` закрывает сессию до записи блока [подтв.]
**Где:** `server/app/modules/learning/service.py::finish_session`.
**Что:** первая транзакция ставит `status=finished, state=done`; потом `_write_block` (LLM `block_writer` до 3 попыток + categorizer + возможный `runbook_writer`). Ошибка LLM / `KeyError` в `_writer_out_to_draft` (`c["term"]`, `p["machine"]` для `list[dict]`) → сессия уже закрыта, блока нет, повторный `finish` запрещён (`can_finish`). Урок на 30 минут потерян — прямое нарушение ядра продукта.
**Фикс:** сначала сгенерировать/сохранить блок, потом закрывать сессию (или статус `finishing` + идемпотентный ретрай «закрыта без блока → сгенерировать»). `BlockWriterDraft.concepts/practice` типизировать pydantic-моделями (`ConceptIn`, `PracticeStepIn`), а не `dict`.
**Тест:** fake LLM падает на block_writer → `finish_session` бросает, сессия остаётся `active/debrief`, повтор с рабочим LLM создаёт блок.

### R-04 Промпты обещают инструменты, которых нет у агента [подтв.]
**Где:** `server/app/modules/chat/agents.py` (`free_chat.tools`, `root.tools`), промпты `root/prompt.md`, `free_chat/prompt.md`, `chat/domain.py` (подсказки претрекера), `service.py::RESEARCH_DIRECTIVE`.
**Что:** `AgentRuntime._schemas_for` отдаёт модели только инструменты из `spec.tools`, остальное — `unknown_tool`. У `free_chat`/`root` нет: `add_source`, `process_source`, `get_job`, `start_activity`, `preview_note` (есть только мгновенный `save_note`), `create_course`/`add_course_item`. А промпты, претрекер и ресёрч-директива прямо велят `add_source → process_source`; UI-кнопки: «Собрать курс» (префилл), «Конспект в базу знаний» (просит превью). Следствие: поток «предложил карточкой → пользователь согласился → добавил» упирается в «инструмент недоступен»; root без `preview_note` может сохранить конспект без апрува, ломая «превью → апрув».
**Фикс:** выдать root нужные tools (`add_source`, `process_source`, `get_job`, `start_activity`, `preview_note`, `create_course`, `add_course_item`, `list_courses`) — или делегировать через `run_agent`.
**Профилактика (обязательно):** тест-линтер «промпт ↔ инструменты»: для каждого агента вытащить из `prompt.md` и `RESEARCH_DIRECTIVE`/`INTENT_DIRECTIVES` идентификаторы в бэктиках вида `name(` / `` `name` `` и проверить, что они ∈ `spec.tools ∪ skills` или не являются инструментами (белый список). Такой тест поймал бы всё выше.

### R-05 Субагент теряет карточки [подтв.]
**Где:** `server/app/modules/chat/tools.py::_collect_subagent`.
**Что:** собирает только `text/usage/tool_start/error`, события `card` игнорируются. `git_prepare_change` (карточка ветки), `propose_change` (дифф с «Применить»), `preview_note`, `show_chapter_review` — результат субагента показывается только как `subagent_result` с 600 символами summary. Ветка/правка промпта создана, а человеку не показана и не может быть одобрена (в вебе нет списка pending-изменений и веток).

Добавить в веб экран «Ожидающие правки» (`/api/tuning/changes?status=pending`, `/api/revision/branches`).
**Тест:** root → `run_agent(auditor)` со сценарием `git_prepare_change` → в SSE родителя есть карточка `git_change`.

### R-06 Песочница скиллов не изолирует [подтв.; доступ к /repo/.env — проверить на проде]
**Где:** `server/app/modules/skills/loader.py::_exec`, `docker-compose.yml`, `modules/skills/tools.py`.
**Что:** subprocess запускается с `env={**os.environ, ...}` → скрипт видит `ZAI_API_KEY*`, `LEARNOS_TELEGRAM_TOKEN`, `TAVILY/SERPER`, GitHub-токен. `LEARNOS_WRITE_DIR` = весь `data_dir` (включая `learnos.db`), запись «только туда» — договорённость, не ограничение. Рабочая копия смонтирована `./:/repo:ro` — по README на проде там лежит `.env` с ключами; `SECRET_FILE_RE` защищает только `repo_read`, а `open('/repo/.env')` из скилла — нет. Сеть открыта. Цепочка атаки: `web_read` (недоверенный текст) → prompt injection → `save_skill` (у `root`/`free_chat` есть и то и другое) → скрипт читает ключи и отправляет наружу. Подтверждения человеком нет (в отличие от `propose_change`).
**Фикс (по возрастанию):**
1. Чистый env для subprocess (whitelist: `PATH`, `LEARNOS_WRITE_DIR`, `LEARNOS_SKILL_*`), без ключей.
2. `LEARNOS_WRITE_DIR` → `data/skill-work/<owner>/<skill>/`; `cwd` там же.
3. Не монтировать `.env` в `/repo` (смонтировать подкаталоги/использовать `git archive` копию без секретов; секреты — только через env контейнера).
4. `save_skill` новых скриптов — через карточку с подтверждением (как `propose_change`) либо `network: false` по умолчанию (отдельный контейнер/`unshare -n`), `resource.setrlimit` (CPU/память).
5. Разделить права: агент, читающий веб (`web_read`), не должен одновременно иметь `save_skill` + `send_telegram_text` (принцип «lethal trifecta»).
**Тест:** скилл `os.environ.get("ZAI_API_KEY")` → `None`; попытка писать в `learnos.db` вне WORK_DIR — отказ/ошибка.

### R-07 Нет авторизации, `CORS *` [подтв.]
**Где:** `server/app/main.py` (CORSMiddleware `allow_origins=["*"]`, MCP без auth), `docker-compose.yml` (порты 8765/3000 наружу).
**Что:** любой в LAN — и любая веб-страница, которую вы откроете (CORS `*` + DNS-rebinding) — может дергать `/api/*` и `/mcp`: удалять данные, менять `connectivity` (прокси → перехват трафика), `tuning/changes/{id}/approve`, `mcpext` (подключить чужой MCP), `/mcp` инструменты `run_checks` (запуск pytest до 900 с — DoS), `repo_read`, `git_prepare_change`, `send_telegram_text`.
**Фикс:** один статический bearer-токен (env `LEARNOS_API_TOKEN`) в middleware + проверка `Origin`/`Host`; CORS — только origin веба; Next-прокси добавляет токен на сервере (браузер его не видит); MCP-клиентам — тот же токен; `/mcp` по умолчанию без «опасных» модулей (revision/tuning/mcpext/messenger).
**Тест:** запрос без токена → 401; запрос с чужим `Origin` → 403.

## P1 — высокий приоритет

### R-08 SSRF обходится [подтв.]
`library/service.py::_assert_public_http_url` защищает только `from_url`. Не защищены: `research/service.py::_fetch` (`web_read`, `extract_chapters`) — агент может читать `http://192.168.0.105:8006`, `http://server:8765/api/...`, metadata-адреса; `POST /sources` kind=web c произвольным url → `process_source` → `_run_web` → `_fetch` без проверки. Кроме того: `follow_redirects=True` (редирект на внутренний адрес), проверка DNS отдельно от соединения (rebinding/TOCTOU).
**Фикс:** единая функция `safe_fetch(url)` в `kernel`/`research`: резолв один раз, проверка всех A/AAAA, ручной обход редиректов с проверкой каждого hop, коннект по проверенному IP (httpx transport с `local_address`/кастомный резолвер); использовать везде (`web_read`, `_run_web`, `_probe_pdf`, `github`). `allow_private_url_fetch` оставить как явный opt-in.

### R-09 `list_blocks` не возвращает связи [подтв.]
`knowledge/infra/sql_repo.py::BlockRepository.list` → `_row_to_meta` (`tags=()`, `sources=()`). `api.py::_card_with_relations` ничего не добавляет (название обманчиво) → в REST/MCP/агентском `list_blocks` теги и источники всегда пустые; в вебе `BlockCard` не показывает источник/теги. Побочно: `courses/service.py::_item_done` для `item_type="chapter"` проверяет `m.sources` → **главы курса никогда не отмечаются пройденными**; следствие для `next_step`.
**Фикс:** в `list` делать батч-подгрузку `block_tags/block_sources/block_links` для выбранных uid (2–3 запроса `IN (...)`); добавить тест на `list_blocks` с источником + `_item_done` для главы.

### R-10 Источник «залипает» в `processing` [подтв.]
`library/worker.py`: job `running` при падении процесса не возвращается в `queued`; `_fail` помечает job, но **не** `sources.status`. `process_source` отказывает при `status=processing` без `force`, а UI не умеет `force`. Итог: книга «обрабатывается…» вечно; `skills.run` может бросить (MemoryError/fitz) → `_run_process` без try/except.
**Фикс:** на старте lifespan — `running`-jobs → `queued` (идемпотентные) или `failed` + источники `processing → failed`; `_fail` обновляет источник; обернуть `_run_process` в try/except; в UI кнопка «Повторить обработку» (`?force=true`); ограничить время job.

### R-11 Дубли активностей [подтв.]
`learning/service.py::start_activity` всегда `INSERT`. Каждый клик «Быстрый разбор/Сессия/Обсудить главу» (`source-actions.tsx`, `reader.tsx`, `study-flow.tsx`) создаёт новую активность с курсором 1; страница источника показывает первую активную, `mark_chapter_done` двигает курсор **той**, что привязана к разговору → прогресс книги размазан по N активностям.
**Фикс:** get-or-create по `(source_id, course_id, status=active)`; миграция слияния дублей (max cursor).

### R-12 История и контекст разговора [подтв.]
`chat/service.py::_build_history`: в историю идут только `user/assistant` с текстом. Результаты инструментов и tool_calls (колонки в `messages` есть, не используются) теряются; карточки (`action_offer`, `note_draft`, `chapter_review`) агент в следующих ходах не видит. ### R-13 Интенты и правила специалистов (архитектурный) [подтв.]
`stream_reply` добавляет `INTENT_DIRECTIVES[intent]` только в **текущий** ход. Со второго сообщения агент не знает сценария. ### R-14 Jinja ломает промпты [подтв.]
`agent/runtime.py` рендерит `prompt.md` и **кастомные/настроенные пользователем** промпты через Jinja (`StrictUndefined`). Любая `{{ … }}`/`{% … %}` в тексте (Docker `--format '{{.Names}}'`, Helm `{{ .Values }}`, Go-шаблоны — типичный DevOps-контент, который легко попадёт в промпт хомлаб-агента) → `UndefinedError/TemplateSyntaxError` → агент падает на каждом запуске.
**Фикс:** переменные подставлять `str.replace`/`string.Template` по явному списку (в коде используются разве что тестовые `{{ x }}`); либо экранировать пользовательские промпты (`{% raw %}`). Валидировать промпт при `stage_change`/`create_custom_agent` пробным рендером.

### R-15 Override-промптов и tuning [подтв.]
- Override **замещает** файл целиком: правка базового промпта в коде (новый инструмент/правило, как T-045) молча не доходит до «настроенных» агентов. Хранить `base_sha` в override и показывать «база изменилась» + 3-way merge/дифф; либо хранить пользовательские правки как дополнение (`overlay`), а не копию.
- `apply_change` не сверяет текущий текст с `old_content` → две pending-правки на одного агента: вторая затирает первую.
- `reject_change` не проверяет статус → `applied` можно «отклонить» (статус врёт, поведение применено).
- LLM обязана выдавать **полный** новый промпт — риск потери правил. Лучше patch-операции (`str_replace`) с валидацией, что якоря найдены.
- Два источника правды о `data_dir`: `resolve_prompt_path` читает `os.environ["LEARNOS_DATA_DIR"]` или `cwd/data`, а `TuningService._override_path` — `settings.data_dir` (по умолчанию `REPO_DIR/data`). Без env (локальная разработка) применённые правки не подхватываются. Брать оба из `Settings`.
- В вебе нет списка pending-правок (см. R-05).

## Архитектура: куда двигаться (harness для обучения)

### A. Handoff вместо «root + одноразовые субагенты» (закрывает R-13, часть R-04/R-12)
Сейчас два режима: `run_agent` (одноразовый, без истории — подходит для аудита, repo-scout) и root, который «сам ведёт» уроки без правил специалистов. Нужен третий примитив — **передача разговора**:
- `conversations.active_agent` (вместо `mode`; старые режимы мигрируют в значения `free_chat/quick_reviewer/session_tutor/prompt_tuner/agent:<name>`).
- Интент при первом сообщении выставляет `active_agent` (review→`quick_reviewer`, session→`session_tutor`, tune→`prompt_tuner`, reinforce→`reviewer`), root остаётся роутером и для одноходовых задач.
- Инструмент `handoff(agent, reason)` и `handoff_back()` для возврата; в UI — бейдж «сейчас ведёт: …».
- Директивы интента перестают быть «одноразовой вставкой» — они часть промпта специалиста (тестируемого и настраиваемого отдельно).
Итог: педагогические правила лежат в одном месте, root становится тонким (меньше схем инструментов в каждом запросе — сейчас ~60).

### B. Слой управления контекстом (R-01, R-12)
1. `ToolResult` как явный тип: `data`, `card`, `window` (offset/next_offset/total), `truncation` (что и сколько отрезано), `summary_for_history`.
2. Бюджетирование по токенам, а не символам; приоритеты: system → профиль → цель сессии → последние ходы → сжатая история → результаты инструментов.
3. Компактация: роль `fast` пишет `conversation.summary` при переполнении; tool-результаты в истории — сжатые резюме.
4. Лазурная загрузка инструментов: root видит каталог (имя+1 строка), полную схему подгружает по `tool_search` — убирает раздувание промпта.
5. Prompt caching (стабильный префикс: system+профиль+схемы) — снизит стоимость при длинных сессиях, если провайдер поддерживает.

### C. Модель знания и повторений (R-17, R-18)
Сейчас единица обучения — блок (MD) с текстовыми `weak_spots`. Предлагаю добавить в БД (MD остаётся каноническим для чтения человеком):
- `concepts(uid, block_uid, term, definition, source_uid, chapter)` — из `BlockDraft.concepts`.
- `assessments(id, concept_uid|block_uid, session_uid, question, answer, verdict, quality 0–5, ts)` — каждый фейнман-вопрос/ответ структурно (сейчас лежит только в `transcript_json`).
- `review_items` переключить на уровень понятия/вопроса (SM-2 на `concept_uid`), блок = агрегат.
- `learner_state` (поверх assessments): уровень освоения по темам/категориям — тьютор адаптирует глубину, а `reinforce` выбирает «самое слабое/созревшее» запросом, а не LLM-догадкой.
- Принуждение: фейнман-гейт (R-18), `weak_spots` блока детерминированно из `assessments`, пометка блока `verified`.
- Дополнить приёмами: чередование (interleaving) тем в `reinforce`, retrieval-first (сначала вопрос, потом материал), генерация вопросов на применение (не только «объясни»), рубрика оценки в `review_examiner` (корректность / полнота / пример).

### D. Единое «ядро знания» без расхождения MD ↔ БД (R-02, R-09, R-21)
Выбрать каноническое представление блока: JSON-драфт (структура) + рендер в MD. Правки — над структурой; `reindex` восстанавливает индекс из JSON/MD без потерь (включая `category_status`); версии — по структуре (diff осмысленный). `kb/` — отдельный git-репо с авто-коммитом на каждое сохранение.

### E. Безопасность и права инструментов (R-06, R-07, R-08)
- Классы инструментов: `read`, `write_kb`, `exec`, `external_effect` (Telegram/MCP/скачивание), `admin`. У каждого агента — разрешённые классы; `exec` и `admin` — только с подтверждением человека (карточка).
- Правило «недоверенный ввод не соседствует с `exec`»: агент с `web_read/github_file` не получает `save_skill`; скиллы создаёт отдельный агент-«скриптер», которому недоверенный контент передаётся как данные.
- Песочница скиллов: отдельный контейнер/`bwrap`/`nsjail`, без секретов, без сети по умолчанию, лимиты CPU/RAM/диска, собственный WORK_DIR.
- Единый auth-слой (R-07), единый `safe_fetch` (R-08), аудит-лог действий с побочными эффектами.
