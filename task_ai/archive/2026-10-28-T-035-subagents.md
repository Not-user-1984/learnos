## Что нужно

Фундамент оркестратора: любой агент может вызвать другого агента как субагента,
трейсы связываются, корневой агент-оркестратор получает режим `root`. Работаем
в ветке `t-034-orchestrator` (см. T-034, решения и аудит там же).

1. **Инструмент `run_agent(name, task, context?)`** (модуль `agent` или `chat`,
   по контракту существующих ToolSpec):
   - берёт `AgentSpec` из `AgentRegistry` (builtin + кастомные), запускает
     `AgentRuntime.run` с задачей в user-сообщении, `system_extra` из `context`;
   - **офлоад из event loop**: `ToolRegistry.call` сейчас синхронный и выполняется
     в async-цикле рантайма (`agent/runtime.py:164-173`) — долгий субагент
     заблокирует сервер; офлоад через `anyio.to_thread` (или async-путь вызова,
     если дешевле);
   - отмена: `CancellationToken` родителя прокидывается субагенту;
   - результат: итоговый текст субагента + агрегаты (steps, tool_calls, токены);
   - рекурсия: субагент может звать субагентов (тем же инструментом), но глубина
     ограничена константой (например 2), чтобы не зациклиться.
2. **`parent_run_id` в БД**: миграция Alembic (колонка в `agent_runs`), запись в
   `DbRunRecorder` (сейчас выбрасывается — `agent/recorder.py:32`). Субагент
   пишет `parent_run_id` = run_id родителя.
3. **Инструмент `list_agents`**: имена, описания, инструменты каждого агента из
   `AgentRegistry` — каталог для оркестратора.
4. **Корневой агент `root`** (builtin, модуль chat): промпт-оркестратор — видит
   `list_agents`, `run_agent`, все инструменты free_chat; правила: сначала
   попытаться самому для простых вопросов, субагент — когда есть подходящий
   специалист; передавать субагенту задачу, а не «разберись сам»; пользователю —
   коротко, кто и что сделал. Режим чата `root` регистрируется в `AGENT_BY_MODE`
   (`chat/service.py`) и становится дефолтом для новых разговоров в API
   (UI переключается в T-039).
5. **Видимость в чате**: вызов субагента отображается существующим чипом
   инструмента (`run_agent: repo_scout`); итог субагента — карточкой (тип
   `subagent_result`: агент, задача, краткий итог, токены). Живой стрим
   субагента — вне этой задачи.

- [x] api/agent-тест: root-агент через сценарный FakeLLMProvider зовёт
      `list_agents` → `run_agent("repo_scout", ...)`; субагент выполняется,

      ограничивается (3-й уровень вложенности отклоняется внятной ошибкой).
- [x] Долгий субагент не блокирует параллельный запрос (тест с двумя
      одновременными вызовами).
- [x] `agent:<name>` и старые режимы работают как раньше (контракт-тест).
- [x] Проверки зелёные (ruff/format/lint-imports/pytest). Коммиты в ветке
      `t-034-orchestrator`; после готовности — статус «ждёт ревью ZCode» в
      этом файле, задача не закрывается до ревью и мерджа.
