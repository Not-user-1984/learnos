## Что было нужно
В настройках — подключение сторонних MCP-серверов: кинул ссылку или конфиг/файл → нейронка
разобрала → сервер проверил → инструменты появились у агентов. Сохранение переживает
рестарты, нерабочие серверы не роняют приложение; дефолтные подключения — из git.

## Сделано
- Модуль `mcpext` (миграция 0006): таблица external_mcps, REST `/api/mcpext` (list/probe/draft/create/refresh/delete).
- `mcp_designer` (LLM): ссылка/JSON/описание → конфиг (имя, url, headers).
- Gateway на mcp SDK (streamable http): каждое соединение — новое; ошибки → понятный текст (ExceptionGroup разворачивается).
- Обёртки `mcp_<сервер>_<инструмент>` в ToolRegistry (канал agent): доступны кастомным агентам через конструктор, live-регистрация без рестарта; `list_external_mcps` — статический инструмент-каталог.
- Безопасный старт: обёртки регистрируются в lifespan по кэшу из БД; probe на старте не делается; недоступный сервер = status=error, приложение живо.
- Дефолты из git: `server/config/external-mcp.json` импортируются при старте (если отсутствуют в БД).
- Веб: секция «Сторонние MCP» в настройках — список со статусами, конструктор (Разобрать с нейронкой → Проверить → Подключить), обновление, отключение.

## Проверено
- 121 тест (probe безопасен, draft-парсер, валидации, обёртки register/unregister, remote_unavailable).
- Живой e2e: наш собственный /mcp подключён как сторонний (51 инструмент, обёртки в каталоге агентов), кастомный агент вызвал `mcp_learnos_core_get_profile` через SSE — ответ ядра получен.

## Ограничения
- Только remote MCP (http/s). Локальный stdio (npx…) — в бэклоге (нужен node в контейнере).
