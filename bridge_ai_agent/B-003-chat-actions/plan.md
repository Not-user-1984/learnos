# B-003 · Чат: одна зона действий, без дублей, перекрытий и зомби-кнопок

Цель: после ответа нейронки пользователь видит один понятный набор действий. Кнопки не дублируют
друг друга, не перекрываются, после клика не возвращаются после перезагрузки.
Контекст: `bridge_ai_agent/docs/system-review-2026-11.md` §2.

## Готово, когда
- [ ] В одном сообщении ассистента не больше одной группы кнопок-решений (`action_offer`/`quick_replies`).
- [ ] Статус карточек с решениями хранится на сервере; после reload нажатые кнопки неактивны и показывают
      выбор («✓ Да», «Применено», «Отклонено»).
- [ ] Ряд чипов над композером один, контекстный, скрыт, пока у последнего сообщения есть неотвеченные решения
      и пока идёт стрим.
- [ ] На ширине 375px ни одна кнопка не перекрыта кнопкой сессии или котом (проверка скриншотом в preview).
- [ ] Команда показывается один раз (карточка `command` или fenced-блок, не оба).
- [ ] Проверки зелёные.

## Изменения
1. **Сервер: статус карточки.**
   - Каждой карточке при эмите — `card_id` (короткий uid), если нет.
   - `POST /api/conversations/{uid}/cards/{card_id}/resolve` body `{choice: str}` → пишет
     `status="resolved"`, `choice` в JSON карточки сообщения; идемпотентно (повтор → 200 с тем же choice;
     другой choice → 409). Сервис-метод в chat-сервисе (новый небольшой класс `CardState` в
     `modules/chat/cards.py`, не раздувать `service.py`).
   - `prompt_change`/`git_change`: при apply/reject (уже существующие эндпоинты tuning/revision) так же
     помечать карточку в сообщении (по `card_id` из запроса; web его передаёт).
2. **Сервер: одна группа решений на ход.** В рантайме при эмите `action_offer`/`quick_replies`, если в этом
   ходе уже есть карточка-решение, — сливать: варианты новой добавляются к первой (без дублей по label),
   вторая не эмитится. Тест на это.
3. **Web: карточки читают статус** из `card.status/choice`; клик → `resolve` → затем отправка сообщения как
   сейчас. После resolve кнопки заменяются строкой выбора. `note_draft`: после «Записать в базу» и пришедшего
   `block_saved` в том же разговоре — note_draft показывает «Записано → Открыть блок» и скрывает кнопки.
4. **Web: дубль команды.** Если в сообщении есть карточка `command` с тем же текстом, что fenced-блок,
   fenced-блок не рендерить (сравнение по trim-строке).
5. **Web: чипы → `NextSteps`.** Новый компонент `chat/next-steps.tsx`: вычисляет 0–3 действия из состояния
   (сессия и фаза / режим разговора / есть ли неотвеченные решения / стрим). В сессии — только действия
   текущей фазы (одно основное). Вне сессии — «Закрепить», «Конспект», «Собрать курс» с ОДНИМ поведением,
   тем же, что на стартовом экране (вынести общий `scenarios.ts`, использовать в обоих местах).
6. **Web: перекрытия.** Кнопку сессии на мобиле перенести в шапку разговора (иконка в header), убрать `fixed`.
   Кота сдвинуть: toggle внутри ряда NextSteps/композера, не поверх ленты; у ленты `padding-bottom`,
   равный высоте полки кота, когда она открыта.
7. **Web: без прыжка.** liveCards во время стрима рендерить тем же компонентом в disabled-состоянии
   фиксированной высоты, после done — заменять без refresh всей ленты, если данные совпадают.
8. **Рефакторинг по пути:** `cards.tsx` разнести по файлам `chat/cards/<type>.tsx` + `index.ts` с реестром
   `type → компонент`. Поведение не менять сверх пунктов выше.

## Тесты
- server: resolve идемпотентен, 409 на другой choice; слияние двух решений в одном ходе;
  история отдаёт `status/choice`.
- web: `tsc`, lint, build; ручная проверка в preview (desktop + 375px): ответ с оффером → клик → reload →
  кнопки неактивны; в сессии один ряд действий.

- Не трогать дизайн-токены: только семантические (`web/DESIGN.md`).
