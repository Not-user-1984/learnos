## 0. Продуктовая рамка (во что целимся)

LearnOS — **второй мозг на двоих**: человек и нейронки пишут и читают одну базу.
- Для человека: «учебная доска» как bridge — курс = доска, элемент курса = задача со статусом
  `todo → doing → review (повторение) → done`; всегда видно «что делать дальше».
- Для нейронки: MCP, где за **1 вызов** кладёшь материал и за **1 вызов** получаешь контекст по теме.
- Система сама себя улучшает: по расписанию ищет проблемы и идеи → задачи → ветки → человек мерджит.

Главный разрыв сейчас: **«сделано» не становится «засчитано»** — сессия не закрывает элемент курса,
не планирует повторение; глобального «что дальше» нет.

## 1. Архитектура сервера

Хорошо (сохранить):
- Модульный монолит `server/app/modules/<name>/{domain,service,api,tools,infra}`; REST и MCP — тонкие
  обёртки над одним `service.py`, дублирования нет.
- import-linter (`server/pyproject.toml:71`): kernel/llm/agent не зависят от модулей; домен не знает infra;
  infra модулей независимы.
- EventBus есть (`app/kernel/events.py:31`, публикация после коммита UoW `kernel/db.py:53`), но
  подписчик один — search (`modules/search/__init__.py:31`).

Проблемы:
- **God-сервисы**: `chat/service.py` 963 стр. (SSE-стрим, компактизация, титулы, интенты/сценарии,
  драфты блоков, review-прогресс), `library/service.py` 866, `knowledge/service.py` 754.
- **Скрытые связи через ленивые импорты** в телах функций (линтер их пропускает):
  `learning/service.py:502` → `knowledge.schemas`, `chat/service.py:856` → `knowledge.agents/service`.
  knowledge — неявный хаб для learning/chat/review.
- **Кросс-модульные эффекты делаются прямыми вызовами**, а не событиями: finish_session сам пишет блок,
  а курсы/повторения ни о чём не узнают.
- `knowledge/infra/sql_repo.py` 455 — смешаны блоки, версии, связи.

Требования к архитектуре (для расширяемости):
1. Межмодульные эффекты — **через доменные события** (`SessionFinished`, `ChapterRead`, `BlockSaved`,
   `CourseItemDone`). Модуль подписывается в `subscribe(bus, container)` — как search.
2. Синхронные межмодульные вызовы — **только через порт** (Protocol в `modules/<x>/ports.py` или фасад),
   никаких ленивых импортов чужих `service/agents/schemas`. Добавить контракт import-linter.
3. Ни один `service.py` > ~500 строк: use-case-классы в `modules/<x>/usecases/`.
4. Новый функционал = новый модуль + подписки, а не правка chat/service.

## 2. UI чата: кнопки дублируют и перекрывают (жалоба пользователя — подтверждена)

Источники кнопок под ответом (`web/src/components/chat/cards.tsx`, `chat-view.tsx`):
карточки `action_offer`, `quick_replies`, `command`, `note_draft`, `block_saved`, `prompt_change`,
`git_change`; ActionLink-меню в markdown; ряд чипов между лентой и композером
(«Фейнман-вопросы», «Закрепить пройденное», «Конспект в базу знаний», «Собрать курс»); оверлеи.

Дубли смысла:
- `offer_action` + `offer_replies` в одном ответе → две группы решений.
- В сессии «что дальше» ×3: чип «Фейнман-вопросы» + quick_replies + текст `question`-карточки.
- «Закрепить/Конспект/Собрать курс» есть и на стартовом экране (`chat-start.tsx:208-210`, prefill),
  и чипами (`chat-view.tsx:505-526`, другое поведение при той же надписи).
- «Копировать» команду ×2: fenced-блок + `command`-карточка.
- `note_draft` «Записать в базу» и следом `block_saved` «Открыть блок».

Перекрытия:
- `fixed bottom-24 right-4 z-20` кнопка сессии на мобиле (`chat-view.tsx:687`) — над чипами и композером.
- Кот: toggle `absolute bottom-2 right-2 z-20` (`chat-cat.tsx:191`) — перекрывает правый край кнопок
  последнего сообщения.
- Во время стрима карточки без кнопок, после `done` — refresh с кнопками: прыжок высоты.

Зомби-кнопки (статус только в `useState`):
- `action_offer`/`quick_replies` (`cards.tsx:59,99`), `note_draft`, `prompt_change` (`card.status ?? "pending"`),
  `git_change` — после перезагрузки снова активны.

Требование: **у сообщения ровно одна зона действий**, статус карточки хранится на сервере,
контекстные «следующие шаги» — одна строка, вычисляемая из состояния, и прячутся, когда у последнего
сообщения уже есть решения.

## 3. Петля обучения

Есть: курсы (planner → from-plan), источники/главы, activities + «прочитал сам», сессия-стейт-машина
(theory → check → practice → debrief → done, `learning/domain.py`), блок из сессии (verified),
SM-2 (`review/domain.py`).

Дыры:
- Блок из сессии без `block_sources` (`learning/service.py:~513`, `activity_uid=None`) → элемент курса
  типа chapter никогда не done.
- «Прочитал сам» блока не создаёт → chapter-элемент курса не закрывается.
- У course_item нет статуса; прогресс деривационный с N+1 (`courses/service.py:281`); курс вечно `planned`;
  `chapter_idx=None` не закрывается никогда.
- Сессия хранит course_id, но не item; web не умеет начать сессию по элементу курса — только через агента.
- `finish_session` не заводит `review_items`: повторение появляется случайно (лениво при запросе очереди).
- Повторений нет в UI (нет REST, нет страницы, нет бейджа), нет напоминаний.
- `/` = сетка KB; дашборда «что дальше» нет; `next_step` курса — текст без кнопки.
- Чтение и обсуждение разорваны: читалка → `router.push('/chat/…')`, split-view нет; видео-плеера и
  таймкодов нет (`_parse_vtt` в `skills/youtube-to-summary/run.py:37` выкидывает тайминги).

## 4. MCP как «второй мозг»

76 тулов в `/mcp` (+ `/mcp/<module>`). Проблемы:
- **Нет «положить быстро»**: `save_note` пишет сразу `confirmed` (`knowledge/tools.py:31`), минуя сессию и
  inbox; inbox есть (`knowledge/service.py:231`, `/api/kb/inbox`), но MCP туда писать не умеет.
- **Нет «дай всё по теме»**: search только FTS5, путь search → get_block → read_chapter = 3–5 вызовов;
  `get_block`/`list_blocks`/`export` без лимитов размера.
- Нет idempotency: `add_source` по тому же URL = дубль (`library/service.py:95`), `save_note` = копия.
- Нет batch. Нет MCP resources/prompts (`kernel/tools/mcp_adapter.py:45` только add_tool); instructions
  сервера — одна строка; у полей pydantic нет `description` → агент не понимает параметры.
- Дубли: `search`/`search_chunks`, `web_search`/скилл `web-search`/`research_sources`,
  `propose_prompt_change`/`propose_change`, `offer_action`/`offer_replies`.

Решение правила «блок только через сессию»: два класса знаний.
- `verified=true` — блок из сессии («проговорено»), единственный, кто считается выученным.
- `inbox` / заметки — сырьё от нейронок и человека, `verified=false`; видно, ищется, отдаётся в контекст,
  помечено как непроверенное; превращается в verified только через сессию.
